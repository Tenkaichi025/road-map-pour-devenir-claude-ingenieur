Leçon 4.2

Cadrer un prompt et le contexte

L'idée

L'IA n'est pas télépathe. Tout ce que ton prompt ne dit pas, elle le décide à ta place : quelle bibliothèque utiliser, comment arrondir un montant, que faire d'une donnée invalide, combien de fichiers créer. Et elle comble ces vides avec des choix « génériques », souvent plus compliqués que nécessaire, rarement adaptés à ton projet.

La qualité du code produit suit donc la clarté de deux choses. Le périmètre : ce qu'il faut faire, les règles, les cas limites, ce qui est hors sujet, et comment savoir que c'est fini. Et le contexte : les fichiers utiles, les conventions du projet, les commandes de test. Les règles durables vont dans un fichier CLAUDE.md, que Claude Code lit à chaque session. La demande du jour va dans le prompt.

Cadrer ne veut pas dire tout dire. Le bon contexte, c'est assez pour comprendre, et rien qui fasse dévier : ni secret, ni données réelles, ni « tout le projet au cas où ».

Exemple concret

Le panier d'une boutique de pagnes, en Node.js : un catalogue, des fonctions pures, des montants en francs CFA entiers, des tests. On veut ajouter des codes promo. Même projet, même besoin, deux prompts.

Le prompt flou

Ajoute un système de remise.

Voici une réponse typique :

package.json                         ← dépendance ajoutée : decimal.js
config/remises.json                  ← un fichier de configuration
src/remises/RemiseStrategy.js        ← une classe « abstraite »
src/remises/RemisePourcentage.js     ← une sous-classe
src/remises/RemiseMontant.js         ← une autre sous-classe
src/remises/FabriqueRemise.js        ← une fabrique
src/promo.js
tests/promo.test.js                  ← 2 tests, tous verts
README.md                            ← « pensez à lancer npm install »

return parseFloat(((total * this.config.valeur) / 100).toFixed(2));   ← des centimes de franc CFA

Les tests sont verts. Mais face aux cas limites, ce code tombe 4 fois sur 7. Le code tapé en minuscules est ignoré. 10 % de 2 995 F donnent un total de 2 695,5 F. TABASKI5000 s'applique sous le minimum prévu (le minimum est dans la configuration… mais jamais lu). Et un code inconnu est ignoré en silence. L'IA n'a pas « mal travaillé » : elle a répondu à une question floue avec des choix au hasard.

Le prompt cadré

Contexte : panier d'une boutique (Node.js, CommonJS, aucune dépendance).
Lis CLAUDE.md, src/panier.js et tests/panier.test.js avant de commencer.

Objectif : ajouter des codes promo.

Données : crée src/promo.js, qui exporte totalAvecCode(panier, code).
panier est le tableau de lignes { reference, quantite } de src/panier.js.
Deux codes, écrits dans ce fichier :
- BIENVENUE10 : 10 % de remise ;
- TABASKI5000 : 5 000 F de remise, seulement si le panier fait au moins 30 000 F.

Règles et cas limites :
- un seul code par panier ; insensible à la casse et aux espaces autour ;
- montants en francs CFA entiers : le pourcentage est arrondi vers le bas ;
- code inconnu → erreur « Code promo inconnu. » ;
- minimum non atteint → erreur qui indique le minimum ;
- le total ne descend jamais sous 0.

Contraintes : aucune dépendance, aucune classe, ne modifie aucun fichier existant.
Fini quand : tests/promo.test.js couvre chaque règle et chaque cas limite,
et « node --test » passe.
Hors périmètre : stocker les codes en base, l'interface, les dates de validité.
Si quelque chose n'est pas clair, pose-moi la question avant de coder.

Résultat typique : 2 fichiers (src/promo.js d'une vingtaine de lignes, et ses tests), aucune dépendance, des montants entiers, 7 cas limites sur 7. Les sept rubriques à retenir : contexte, objectif, données, règles et cas limites, contraintes, « fini quand », hors périmètre. Et une phrase qui change tout : « pose-moi la question si ce n'est pas clair ».

Le CLAUDE.md : les règles qui durent

Ce qui vaut pour toutes les demandes ne se répète pas dans chaque prompt : on l'écrit une fois dans le CLAUDE.md à la racine du projet. Claude Code le lit au début de chaque session. Garde-le court (une page) et concret : 

# Panier boutique — règles pour Claude

## Projet
Panier d'une boutique de pagnes. Node.js 22+, CommonJS (require / module.exports).

## Commandes
- Tests : node --test. Ils doivent tous passer avant de me rendre la main.

## Conventions
- Noms en français, verbes à l'infinitif : ajouterAuPanier, totalPanier.
- Montants en francs CFA, toujours entiers. Jamais toFixed ni parseFloat pour l'argent ;
  arrondi : Math.floor.
- Erreurs : throw new Error("Message clair en français.")
- Fonctions pures, données en paramètre. Pas de classe sans nécessité.

## Limites
- Aucune dépendance sans mon accord.
- Ne modifie pas les tests existants ; ajoute un test par règle et par cas limite.
- Ne touche qu'aux fichiers nécessaires ; annonce-moi la liste avant de commencer.

## Sécurité
- Aucun secret dans le code : process.env, et .env ignoré par git (leçon 3.3).
- SQL : requêtes préparées avec « ? » ; liste blanche pour les noms de colonnes (3.1).
- Affichage : textContent, jamais innerHTML avec des données (3.2).
- Chaque requête sur une donnée vérifie son propriétaire (3.5).

## Git
- Branche ia/… ; un commit par étape, messages précis ; jamais de push ni de reset --hard (4.1).

Ce qui n'y va pas : la tâche du jour, les secrets, les longues explications. Dans Claude Code, tu peux aussi citer un fichier précis dans ton prompt avec @src/panier.js, et repartir d'une conversation vide avec /clear quand tu changes de sujet : une vieille discussion hors sujet fait dévier autant qu'un prompt flou.

Vérifier le travail de l'IA

Après chaque réponse, surtout quand ta demande était courte :

  • Aucune dépendance inventée : compare package.json avant et après. Une dépendance doit répondre à un vrai besoin, que tu as accepté.
  • Pas de sur-ingénierie : des classes, des fabriques, des « stratégies » ou un fichier de configuration pour un besoin qui tient en 20 lignes. « Extensible pour plus tard » n'est pas une raison.
  • Les conventions du CLAUDE.md sont respectées : système de modules, noms, montants, messages d'erreur.
  • Seuls les fichiers attendus ont bougé (git diff --stat, leçon 4.1). Un README « amélioré » ou une instruction inventée (« lancez npm install ») sont des signaux.
  • Chaque règle et chaque cas limite de ta demande a son test. Et vérifie le comportement réel, pas seulement que les tests sont verts.
  • Quand ta demande était ambiguë, l'IA a-t-elle posé une question, ou a-t-elle tranché seule ? Repère chaque décision qu'elle a prise à ta place.
  • Aucun secret ni aucune donnée réelle n'a été recopié dans le code, les tests ou les exemples.

À retenir

  1. Ce que le prompt ne dit pas, l'IA le décide à ta place, souvent en plus compliqué.
  2. Un prompt cadré : contexte, objectif, données, règles et cas limites, contraintes, « fini quand », hors périmètre.
  3. Les règles durables (commandes, conventions, limites, sécurité) vont dans CLAUDE.md, court et concret.
  4. Le bon contexte : assez pour comprendre, rien qui fasse dévier. Jamais de secret ni de vraie donnée.
  5. Après la réponse : dépendances, fichiers touchés, conventions, et chaque cas limite vérifié.

Exercices

Les fichiers sont dans exercices/m4-02/ :

  • node preparer-exercice.js <dossier> crée le dépôt d'entraînement (hors du cours) : main avec le tag avant-ia, et deux branches, ia/prompt-flou et ia/prompt-cadre.
  • node controle-ia.js <dépôt> avant-ia contrôle la branche sur laquelle tu te trouves : dépendances, fichiers, volume, sur-ingénierie, conventions, tests existants, résultat des tests.
  • node essais-limites.js <dépôt> soumet le totalAvecCode de la branche aux 7 cas limites.
Exercice 1 · guidé

Comparer les deux réponses

  1. Depuis exercices/m4-02 : node preparer-exercice.js C:\exos\panier.
  2. git -C C:\exos\panier switch ia/prompt-flou, puis lance controle-ia.js et essais-limites.js sur C:\exos\panier.
  3. Fais la même chose sur ia/prompt-cadre.
  4. Lis src/promo.js et src/remises/ de la branche floue. Fais la liste de chaque décision que l'IA a prise seule, faute d'indication dans le prompt.

Résultat attendu : branche floue, 7 points d'alerte et 3 cas limites sur 7 ; branche cadrée, aucun point et 7 sur 7 ; et une liste d'au moins 5 décisions prises à ta place.

Indices

Pour chaque cas limite raté, demande-toi : « mon prompt flou disait-il quelque chose là-dessus ? »

Correction

Les décisions prises à ta place par la réponse floue :

  • quels codes, et quelles valeurs (rangés dans un fichier de configuration) ;
  • une architecture à 4 classes, « extensible » ;
  • une bibliothèque de calcul (decimal.js), déclarée mais même pas utilisée ;
  • des montants à 2 décimales, en francs CFA ;
  • la casse du code compte ;
  • un code inconnu est ignoré, sans erreur ;
  • le minimum de TABASKI5000 est écrit, mais jamais vérifié ;
  • le README est réécrit.

Les deux branches ont des tests verts. Seuls la liste des fichiers, les conventions et les cas limites font la différence. Remarque : la branche cadrée ajoute 55 lignes contre 95, mais surtout plus de tests. Le nombre de lignes n'est qu'un indice, ce qui compte est ce qu'elles font.

Exercice 2 · semi-guidé

Ton CLAUDE.md et ton prompt cadré

  1. Sur main, crée le CLAUDE.md du projet (inspire-toi de celui de la leçon) et commite-le. Puis git tag avant-mon-prompt et git switch -c ia/code-plafonne.
  2. Écris un prompt cadré, avec les sept rubriques, pour un nouveau code : MEGA20, 20 % de remise, plafonnée à 10 000 F. Prévois toi-même les cas limites.
  3. Donne-le à Claude Code, dans ce dépôt.
  4. node controle-ia.js C:\exos\panier avant-mon-prompt, puis vérifie tes cas limites à la main.

Résultat attendu : un CLAUDE.md d'une page, un prompt avec ses sept rubriques, un contrôle sans alerte (ou chaque alerte expliquée), et tes cas limites respectés.

Indices

Cas limites à prévoir pour un plafond : juste en dessous (40 000 F → 8 000 F de remise), pile au plafond (50 000 F → 10 000 F), au-dessus (80 000 F → toujours 10 000 F), un montant qui donne des centimes, et la casse du code.

Correction

Un extrait de prompt correct :

Objectif : ajouter le code MEGA20 dans src/promo.js, sans changer
le comportement des codes existants.
Règle : 20 % de remise, arrondi vers le bas, plafonnée à 10 000 F.
Cas limites (un test chacun) : 40 000 F → 32 000 F ; 50 000 F →
40 000 F ; 80 000 F → 70 000 F ; « mega20 » accepté ; 2 995 F → 2 396 F.
Contraintes : ne modifie que src/promo.js et tests/promo.test.js ;
aucun test existant modifié.
Fini quand : node --test passe.

Si le contrôle signale un test existant modifié, ou un autre fichier touché, refuse et rappelle la contrainte. Et vérifie un calcul toi-même : 20 % de 2 995 F = 599 F, donc un total de 2 396 F.

Exercice 3 · libre

Le CLAUDE.md de ton projet, et un prompt de refactoring

Écris le CLAUDE.md d'un de tes projets (par exemple Royal Senteur) : commandes, conventions réelles (regarde le code existant), limites, sécurité, Git. Puis écris un prompt de refactoring : réorganiser du code sans changer son comportement. Applique-le sur une branche, et contrôle le résultat.

Résultat attendu : un CLAUDE.md fidèle au projet, un prompt de refactoring, et la preuve que le comportement n'a pas changé (tests inchangés et verts, git diff --stat limité aux fichiers prévus).

Pistes
  • Un prompt de refactoring contient toujours : « ne change aucun comportement », « les tests existants ne sont pas modifiés et restent verts », et la liste des fichiers autorisés.
  • Pas de tests sur la partie à refactorer ? Demande d'abord à Claude d'en écrire, vérifie-les, commite-les, et seulement ensuite lance le refactoring.
  • Adapte la liste CONVENTIONS de controle-ia.js aux règles de ton projet : tu as ton propre contrôle automatique.

Teste-toi

1. Au prompt « Ajoute un système de remise », l'IA répond avec une nouvelle dépendance et quatre classes. Pourquoi ?

Sans conventions, ni contraintes, ni cas limites, l'IA décide seule. Elle choisit souvent la solution la plus « générale » possible. Le prompt cadré et le CLAUDE.md lui donnent les réponses qu'elle aurait dû inventer.

2. Qu'est-ce qui a sa place dans le CLAUDE.md d'un projet ?

Le CLAUDE.md est lu à chaque session : il contient ce qui vaut pour toutes les demandes. La tâche du jour va dans le prompt. Et les secrets ne vont nulle part dans la conversation.

3. Que doit absolument contenir un prompt de refactoring ?

Un refactoring réorganise le code sans changer ce qu'il fait. Les tests existants, inchangés, sont la preuve que rien n'a bougé. Si l'IA les modifie, cette preuve disparaît.
