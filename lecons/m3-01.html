Leçon 3.1

Injection SQL : auditer ses requêtes

L'idée

En 2.3, tu as vu la règle de base : une valeur venue de l'extérieur ne se colle jamais dans le texte SQL, elle passe par un ?. Cette leçon t'apprend à auditer un projet entier : trouver toutes les requêtes construites à la main, et décider pour chacune si elle est sûre.

Car l'injection ne se cache pas seulement dans les recherches. Elle se glisse aussi dans le tri (« trier par prix »), les filtres à plusieurs choix (« pagnes et bijoux ») et les messages d'erreur trop bavards. Le tri a une particularité : un ? ne peut remplacer qu'une valeur, jamais un nom de colonne. Il faut donc un autre outil : la liste blanche.

Retiens les trois réponses possibles : une valeur → un ?. Une liste de valeurs → autant de ? que de valeurs. Un nom de colonne ou un sens de tri → une liste blanche, et tout le reste est refusé.

Exemple concret

Le catalogue d'une boutique de pagnes et de bijoux à Treichville. Les clients peuvent chercher un produit, filtrer par catégories et trier par prix. Certains produits ne sont pas encore en vente : ils ne doivent jamais apparaître. Voici le code écrit par une IA pressée : 

// GET /api/produits?q=pagne&categories=pagnes,bijoux&tri=prix&ordre=desc
let requete = "SELECT id, nom, categorie, prix FROM produits WHERE visible = 1";
if (q) requete += ` AND nom LIKE '%${q}%'`;
if (categories) requete += ` AND categorie IN ('${categories.split(",").join("', '")}')`;
if (tri) requete += ` ORDER BY ${tri} ${ordre || "ASC"}`;
return repondre(res, 200, db.prepare(requete).all());

// ...et en cas d'erreur, « pour déboguer plus facilement » :
repondre(res, 500, { erreur: erreur.message, details: String(erreur) });

Quatre problèmes, chacun d'une famille différente :

  • La recherche colle q dans le SQL : c'est le cas vu en 2.3. Une simple apostrophe (« Boucles d'oreilles ») provoque une erreur, et le texte de la recherche peut modifier la requête.
  • Le filtre colle chaque catégorie entre apostrophes : même problème, caché dans une liste.
  • Le tri colle tri et ordre tels quels : n'importe quel texte devient du SQL.
  • L'erreur renvoie le message de la base au visiteur. Par exemple no such column: couleur ou near "au": syntax error. Ces messages décrivent la structure de ta base à quiconque les provoque.

La version corrigée

const TRIS = { nom: "nom", prix: "prix", categorie: "categorie" };   // liste blanche
const ORDRES = { asc: "ASC", desc: "DESC" };

const conditions = ["visible = 1"];
const valeurs = [];
if (q) {
  conditions.push("nom LIKE ?");                                  // 1. une valeur → un ?
  valeurs.push(`%${q}%`);
}
if (categories) {
  const liste = categories.split(",").filter(Boolean);
  conditions.push(`categorie IN (${liste.map(() => "?").join(", ")})`);   // 2. une liste → autant de ?
  valeurs.push(...liste);
}
let requete = `SELECT id, nom, categorie, prix FROM produits WHERE ${conditions.join(" AND ")}`;
if (tri) {
  if (!TRIS[tri] || (ordre && !ORDRES[ordre])) {                       // 3. un nom → liste blanche
    return repondre(res, 400, { erreur: "Tri non autorisé." });
  }
  requete += ` ORDER BY ${TRIS[tri]} ${ORDRES[ordre] || "ASC"}`;
}
return repondre(res, 200, db.prepare(requete).all(...valeurs));

// En cas d'erreur : le détail dans le terminal du serveur, un message neutre pour le visiteur.
console.error(erreur);
repondre(res, 500, { erreur: "Erreur interne. Réessaie plus tard." });

Remarque : la version corrigée contient encore des ${…} dans le SQL. Ce n'est pas un problème, car ce qu'ils insèrent vient de ton code (des ?, ou un nom tiré de TRIS), jamais du visiteur. Un audit ne cherche pas des ${ : il cherche d'où vient chaque morceau inséré.

Vérifier le travail de l'IA

La méthode d'audit, à appliquer à tout code qui parle à une base :

  • Liste toutes les requêtes construites avec une variable : ${…}, +, +=, sur une ou plusieurs lignes. Un outil aide au premier tri, mais il en rate.
  • Pour chaque morceau inséré, demande-toi d'où il vient : du visiteur (adresse, formulaire, JSON, cookie) ou de ton code ?
  • Chaque valeur passe par un ?. Une liste IN génère autant de ? que de valeurs.
  • Les noms de colonnes, ASC/DESC et les noms de tables passent par une liste blanche. Une valeur hors de la liste donne 400, jamais 500.
  • Refuse les « nettoyages » maison (.replace(/'/g, "''"), une liste de mots interdits) : ils se contournent, et ils cassent les données normales.
  • Les erreurs : un message neutre pour le visiteur, le détail dans les journaux du serveur. Jamais erreur.message dans la réponse.
  • Avec un outil qui écrit le SQL à ta place (un ORM comme Prisma, Sequelize ou Knex), cherche les fonctions « brutes » : $queryRawUnsafe, sequelize.query(…), knex.raw(…). Elles demandent les mêmes précautions.
  • Même un id déjà vérifié par une expression régulière passe par un ? : il suffit d'une modification de la regex pour rouvrir la faille.

À retenir

  1. Une valeur → un ?. Une liste → autant de ?. Un nom de colonne → une liste blanche.
  2. Un audit ne cherche pas des ${ : il cherche d'où vient chaque morceau inséré dans le SQL.
  3. Les outils d'audit trient, mais ils ratent des lignes et en signalent d'autres à tort. La relecture reste obligatoire.
  4. Jamais de nettoyage maison du texte : ça se contourne et ça casse les vraies données.
  5. Une erreur SQL ne sort jamais du serveur : message neutre pour le visiteur, détail dans les journaux.

Résultat attendu : un rapport d'audit (ligne, variable, origine, verdict) et, s'il y a des failles, leur correction vérifiée par un test avec une apostrophe.

Pistes
  • Si ton projet utilise un ORM, la plupart des requêtes sont déjà sûres. Concentre-toi sur les fonctions « brutes » : cherche raw, Unsafe, query(.
  • En PHP, cherche mysqli_query et ->query( avec des variables, au lieu de prepare.
  • N'oublie pas les tris et les filtres des pages de liste (boutique, tableau de bord) : c'est là que l'IA colle le plus souvent des noms de colonnes.
  • Teste sur ta machine, jamais sur le site en ligne d'un autre.

Teste-toi

1. Pourquoi ne peut-on pas écrire ORDER BY ? pour un tri choisi par le visiteur ?

La base prépare la requête avant de connaître les valeurs, donc elle doit déjà savoir sur quelle colonne trier. Pour un nom de colonne, on choisit dans une liste fixée par ton code, et on refuse tout le reste.

2. En cas d'erreur, l'API renvoie { erreur: erreur.message }. Quel est le problème ?

no such column: couleur apprend à un inconnu que sa valeur arrive dans le SQL, et comment s'appellent tes colonnes. Message neutre pour le visiteur, détail avec console.error dans les journaux du serveur.

3. WHERE id = ${id}, mais id a déjà été vérifié par la regex \d+. Que décides-tu ?

La regex ne laisse passer que des chiffres : rien ne peut s'injecter aujourd'hui. Mais la sécurité repose alors sur une ligne lointaine que quelqu'un modifiera un jour. Avec un ?, la requête est sûre toute seule.
