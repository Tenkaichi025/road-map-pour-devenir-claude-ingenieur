Leçon 3.2

Faille XSS : protéger l'affichage

L'idée

La faille XSS, c'est l'injection SQL, mais dans la page. Un texte écrit par un visiteur (un avis, un prénom, une recherche) est réaffiché dans une page. Si la page le traite comme du HTML au lieu de le traiter comme du texte, le visiteur peut y glisser des balises, et donc du code. Ce code s'exécute ensuite chez les autres visiteurs, avec leurs droits : il peut agir en leur nom, afficher un faux formulaire de connexion, ou lire ce que la page affiche.

Deux familles. La XSS stockée : le texte est enregistré (un avis, un commentaire, un profil), puis affiché à tous ceux qui ouvrent la page. La XSS réfléchie : le texte vient de l'adresse (une recherche, un message d'erreur) et il est renvoyé tout de suite à celui qui ouvre ce lien.

La protection tient en une règle : au moment de l'affichage, une donnée reste du texte. Dans le navigateur, on utilise textContent plutôt que innerHTML. Sur le serveur, on échappe chaque valeur insérée dans du HTML. Et on ajoute une deuxième ceinture : l'en-tête Content-Security-Policy (CSP), qui interdit au navigateur d'exécuter des scripts qui ne viennent pas de ton site.

Exemple concret

Les avis clients du maquis « Le Baobab ». Les clients publient un avis. La page les affiche à trois endroits, chacun construit d'une façon différente. Pour tester, pas besoin d'attaque : un marqueur inoffensif suffit. Publie un avis signé <b>test</b>. Si « test » apparaît en gras, la donnée a été lue comme du HTML : la page est vulnérable. Si tu vois <b>test</b> tel quel, elle est protégée.

Les trois affichages écrits par l'IA

// 1. Sur le serveur : la liste de tous les avis (XSS stockée)
`<li><strong>${a.auteur}</strong> (${a.note}/5) : ${a.texte}</li>`

// 2. Sur le serveur : le mot cherché, réaffiché (XSS réfléchie)
`<p>Résultats pour « ${q} » : ${trouves.length} avis.</p>`

// 3. Dans le navigateur : les 3 derniers avis
document.querySelector("#derniers").innerHTML = avis.map((a) => `<li>${a.auteur} : ${a.texte}</li>`).join("");

Avec le marqueur, « test » s'affiche en gras aux trois endroits. Et la réponse du serveur n'a aucun en-tête CSP.

Côté serveur : échapper

Échapper, c'est remplacer les cinq caractères qui ont un sens en HTML par leur version « texte ». Le navigateur les affiche, mais ne les interprète plus : 

function echapper(valeur) {
  return String(valeur)
    .replaceAll("&", "&amp;")      // toujours en premier
    .replaceAll("<", "&lt;")
    .replaceAll(">", "&gt;")
    .replaceAll('"', "&quot;")
    .replaceAll("'", "&#39;");
}

`<li><strong>${echapper(a.auteur)}</strong> (${echapper(a.note)}/5) : ${echapper(a.texte)}</li>`
`<p>Résultats pour « ${echapper(q)} » : ${trouves.length} avis.</p>`

Échapper n'est pas « nettoyer ». On ne retire rien, on ne devine pas ce qui est dangereux : on transforme tous les caractères spéciaux, au moment de l'affichage. La donnée enregistrée reste intacte. Les moteurs de gabarits (EJS, Handlebars, Twig, Blade…) le font par défaut, sauf avec leur syntaxe « brute » : <%-, {{{ }}}, |raw, {!! !!}.

Côté navigateur : textContent

const li = document.createElement("li");
const auteur = document.createElement("strong");
auteur.textContent = a.auteur;          // toujours du texte, quoi qu'il contienne
li.append(auteur, " : " + a.texte);     // append d'une chaîne = du texte aussi

La deuxième ceinture : la CSP

Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'

Cet en-tête dit au navigateur : « n'exécute que les scripts qui viennent de mon site, sous forme de fichiers ». Les scripts écrits directement dans la page, ou venus d'ailleurs, sont bloqués. Si une erreur d'affichage passe un jour, la CSP limite fortement les dégâts. Elle ne remplace pas l'échappement : elle le complète. Conséquence pratique : avec une CSP, tout ton JavaScript doit être dans des fichiers .js, sans onclick="…" ni <script> écrit dans la page.

Vérifier le travail de l'IA

Quand l'IA affiche des données venues des visiteurs :

  • Repère tous les endroits où une donnée devient du HTML : innerHTML, insertAdjacentHTML, document.write, du HTML construit avec ${…}, les syntaxes « brutes » des gabarits. Un outil aide, mais il rate le HTML écrit sur plusieurs lignes.
  • Dans le navigateur : textContent pour toute donnée. innerHTML seulement avec du HTML fixe, écrit par toi.
  • Sur le serveur : chaque valeur insérée dans du HTML passe par une fonction d'échappement, ou par un gabarit qui échappe par défaut.
  • Refuse les faux nettoyages : supprimer certains mots ou certaines balises, ne remplacer qu'un seul caractère, ou modifier le texte avant de l'enregistrer. Ces méthodes laissent passer des cas auxquels l'IA n'a pas pensé, et elles abîment les données normales. Si le site doit vraiment accepter du HTML (un éditeur de texte riche), il faut une bibliothèque éprouvée comme DOMPurify, jamais une regex.
  • Pas de double échappement : « C&#39;est » ne doit jamais apparaître à l'écran.
  • Teste les deux familles : les données stockées (avis, profils, commentaires) et réfléchies (recherche, messages d'erreur qui répètent ta saisie, paramètres d'adresse).
  • Un en-tête CSP est envoyé avec script-src ou default-src 'self', et sans 'unsafe-inline'. Quand la CSP bloque un script écrit dans la page, l'IA ajoute souvent 'unsafe-inline'. La vraie correction : déplacer ce script dans un fichier.
  • Une adresse fournie par un visiteur et placée dans un lien doit commencer par https://. Et le cookie de session reste HttpOnly (leçon 2.4).

À retenir

  1. XSS : une donnée de visiteur, lue comme du HTML par la page. Stockée (enregistrée) ou réfléchie (renvoyée tout de suite).
  2. On protège au moment de l'affichage : textContent dans le navigateur, échappement sur le serveur.
  3. Échapper, ce n'est pas nettoyer : on transforme tous les caractères spéciaux, et la donnée enregistrée reste intacte.
  4. La CSP est une deuxième ceinture : 'self', jamais 'unsafe-inline'.
  5. Pour tester, un marqueur inoffensif suffit : <b>test</b> ne doit jamais apparaître en gras.

Exercices

Les fichiers sont dans exercices/m3-02/. Les avis se lancent avec node serveur.js (port 3009). node verifier.js (dans avis) est le banc de test : il publie le marqueur et vérifie 8 points. node audit-xss.js <dossier> (dans outils) repère les endroits dangereux de n'importe quel projet.

Exercice 1 · guidé

Le marqueur, en vrai

  1. Dans exercices/m3-02/avis, lance node serveur.js et ouvre http://localhost:3009.
  2. Publie un avis avec le prénom <b>test</b>. Regarde « Les 3 derniers avis » et « Tous les avis ».
  3. Cherche <b>test</b> avec le champ de recherche. Regarde la phrase « Résultats pour… ».
  4. F12 → onglet Éléments : trouve la balise <b> que ta donnée a créée dans la page.
  5. Onglet Réseau → recharge → clique sur la première ligne → en-têtes de la réponse. Y a-t-il un Content-Security-Policy ?
  6. Dans un deuxième terminal, lance node verifier.js (dans avis), puis node audit-xss.js ../avis (dans outils).

Résultat attendu : « test » en gras aux trois endroits, une vraie balise <b> dans l'onglet Éléments, aucune CSP, 5 échecs sur 8 au banc de test, et la ligne que l'outil d'audit a ratée.

Indices

Compare la liste de l'outil d'audit avec les trois affichages de la section « Exemple concret ». Lequel manque, et pourquoi ?

Correction
  • Trois affichages vulnérables : serveur.js ligne 57 (tous les avis, XSS stockée), serveur.js ligne 101 (la recherche, XSS réfléchie) et public/app.js lignes 4 à 7 (innerHTML).
  • L'outil rate la ligne 101. Le HTML de la recherche est écrit sur plusieurs lignes, et l'outil lit une ligne à la fois : il ne voit pas que ${q} est à l'intérieur d'un gabarit HTML. Comme en 3.1 : un outil trie, il ne prouve rien.
  • Aucun en-tête CSP : rien ne limiterait les dégâts si une erreur passait.
  • Le banc de test : 3 réussis, 5 échecs (les deux pages serveur, la CSP deux fois, innerHTML).

Indices

Le test « L'avis est stocké tel quel » est là pour attraper les nettoyages faits à l'enregistrement, et le test « Pas de double échappement » pour les échappements faits deux fois.

Correction

Le code attendu est celui de la section « Exemple concret ». Les fausses corrections à refuser :

  • Un nettoyage du texte avant l'enregistrement : le test « stocké tel quel » échoue, et les avis légitimes sont abîmés.
  • Une liste de balises interdites ou un .replace qui ne traite qu'un caractère : incomplet par nature.
  • L'échappement fait deux fois (à l'enregistrement et à l'affichage) : « C&#39;est » apparaît à l'écran.
  • 'unsafe-inline' ajouté à la CSP « pour que ça marche » : la protection perd l'essentiel de son intérêt.

Après la correction, l'outil d'audit signale encore la ligne de la liste des avis : elle contient des ${…} dans du HTML. Mais chaque valeur passe par echapper(). C'est une fausse alerte, et c'est à toi de la classer.

Exercice 3 · libre

Auditer l'affichage de ton propre projet

Lance node audit-xss.js sur un de tes projets. Pour chaque ligne signalée, puis pour chaque gabarit HTML écrit sur plusieurs lignes, détermine d'où viennent les données affichées et si elles sont protégées. Ensuite, sur ta version locale, publie le marqueur <b>test</b> dans chaque champ libre (avis, nom, adresse de livraison, message de contact) et regarde partout où il s'affiche, y compris dans l'espace d'administration. Enfin, vérifie si ton site envoie une CSP.

Résultat attendu : un rapport (fichier, ligne, donnée, verdict), la liste des champs testés avec le marqueur, la présence ou l'absence de CSP, et une demande de correction pour Claude.

Pistes
  • Les pages d'administration sont souvent oubliées : c'est pourtant là qu'un avis piégé serait lu par la personne qui a le plus de droits.
  • Pour la CSP, regarde les en-têtes de réponse de la page principale de ton site (F12 → Réseau). Si ton site passe par un hébergeur ou un CDN, la CSP peut se régler dans son tableau de bord.
  • Une CSP stricte peut casser des scripts écrits dans tes pages : note-les, il faudra les déplacer dans des fichiers.
  • Ne teste que tes propres sites.

Teste-toi

1. Le prénom saisi par un client doit s'afficher dans la page. Que choisis-tu ?

textContent affiche exactement ce qui a été tapé, sans jamais l'interpréter. Retirer certains mots est un faux nettoyage : d'autres balises restent possibles, et le prénom est abîmé.

2. L'IA « protège » les avis en modifiant leur texte avant de l'enregistrer dans la base. Qu'en penses-tu ?

Le danger dépend de l'endroit où la donnée est affichée (une page HTML, un e-mail, une application mobile…). C'est donc à chaque affichage de la protéger. Et une donnée abîmée à l'entrée l'est pour toujours.

3. Après l'ajout d'une CSP, un script écrit dans la page ne marche plus. L'IA propose d'ajouter 'unsafe-inline'. Que fais-tu ?

'unsafe-inline' autorise justement les scripts écrits dans la page : c'est ce que la CSP devait bloquer en cas de XSS. Déplacer le script dans un fichier garde la protection, et la page marche.
