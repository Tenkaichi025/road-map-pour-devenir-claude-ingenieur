Leçon 3.5

Contrôle d'accès et IDOR

L'idée

L'authentification répond à « qui es-tu ? » (leçon 2.4). L'autorisation répond à « as-tu le droit de faire cette action sur cette donnée ? ». Un site peut parfaitement vérifier la première question et oublier la seconde.

C'est la faille IDOR (on dit aussi BOLA pour les API). L'adresse contient le numéro de la ressource : /api/factures/3. Si le serveur vérifie seulement que tu es connecté, il suffit de changer le numéro pour lire, modifier ou supprimer la facture d'un autre client. C'est la faille n°1 du classement OWASP des risques des API, et l'une des plus fréquentes dans le code généré par IA.

Sa cousine, c'est l'escalade de privilèges par copie du corps de la requête. Le serveur recopie tout ce que le client envoie ({ ...moi, ...corps }). Le client ajoute alors "role": "admin"… et il devient administrateur. La règle : le propriétaire et le rôle viennent toujours de la session et de la base, jamais de ce que le client envoie.

Exemple concret

Le tableau de bord de l'agence de comptabilité « Compta Plus ». Chaque client voit ses factures. Awa (Awa Couture) a les factures n°1 et n°2, Kofi (Kofi Transport) les n°3 et n°4. Une administratrice voit tout. La connexion est solide (leçon 2.4). Mais voici ce que l'IA a écrit pour une facture précise : 

const facture = db.prepare("SELECT * FROM factures WHERE id = ?").get(id);   // n'importe quelle facture
if (!facture) return repondre(res, 404, { erreur: "Facture introuvable." });

if (req.method === "GET") return repondre(res, 200, facture);
if (req.method === "PUT") db.prepare("UPDATE factures SET statut = ? WHERE id = ?").run(corps.statut, id);
if (req.method === "DELETE") db.prepare("DELETE FROM factures WHERE id = ?").run(id);

Et pour le profil, puis pour l'administration :

// PUT /api/moi : « on met à jour avec ce que le client a envoyé »
const misAJour = { ...moi, ...corps };
db.prepare("UPDATE utilisateurs SET nom = ?, telephone = ?, role = ? WHERE id = ?")
  .run(misAJour.nom, misAJour.telephone, misAJour.role, moi.id);

// GET /api/admin/factures : protégée… par la seule connexion
const moi = exigerConnexion(req, res);
return repondre(res, 200, toutesLesFactures);

Résultat, avec le compte d'Awa : elle lit la facture n°3 de Kofi (1 200 000 FCFA), la marque comme payée, supprime la n°4, envoie "role": "admin" dans son profil, et ouvre l'administration. Sans jamais connaître le mot de passe de personne.

La version corrigée

// 1. Chaque requête sur une ressource précise contient la condition de propriété.
//    moi.id vient de la session : le client ne peut pas le choisir.
const facture = db.prepare("SELECT id, numero, montant, statut FROM factures WHERE id = ? AND client_id = ?")
  .get(id, moi.id);
if (!facture) return repondre(res, 404, { erreur: "Facture introuvable." });   // pas la sienne = introuvable

db.prepare("UPDATE factures SET statut = ? WHERE id = ? AND client_id = ?").run(corps.statut, id, moi.id);
db.prepare("DELETE FROM factures WHERE id = ? AND client_id = ?").run(id, moi.id);

// 2. Le profil : une liste blanche des champs modifiables. Le rôle n'en fait pas partie.
const nom = typeof corps.nom === "string" && corps.nom.trim() ? corps.nom : moi.nom;
const telephone = typeof corps.telephone === "string" ? corps.telephone : moi.telephone;
db.prepare("UPDATE utilisateurs SET nom = ?, telephone = ? WHERE id = ?").run(nom, telephone, moi.id);

// 3. L'administration : le rôle est vérifié par le serveur.
if (moi.role !== "admin") return repondre(res, 403, { erreur: "Réservé à l'administration." });
  • Pourquoi 404 pour la facture d'un autre, et pas 403 ? Un 403 dirait « elle existe, mais pas pour toi ». Un 404 ne révèle même pas son existence.
  • Pourquoi 403 pour l'administration ? Tout le monde sait qu'elle existe. Ce qui compte, c'est que le serveur la refuse, et pas seulement que le bouton soit caché dans la page.
  • Des numéros difficiles à deviner (des UUID) rendent l'attaque moins facile, mais ils ne remplacent pas la vérification : un numéro finit toujours par circuler (un lien partagé, une capture d'écran, un journal).

Vérifier le travail de l'IA

Pour chaque route qui touche aux données d'un utilisateur :

  • Chaque SELECT, UPDATE ou DELETE sur une ressource précise contient la condition de propriété (AND client_id = ?), avec l'id tiré de la session.
  • Les listes, recherches, exports et téléchargements de fichiers aussi : WHERE client_id = ?.
  • PUT, PATCH et DELETE vérifient la propriété comme GET. L'IA protège souvent la lecture… et oublie la modification.
  • Jamais de copie du corps entier (...req.body, Object.assign) dans un objet enregistré : une liste blanche des champs modifiables.
  • role, client_id, utilisateur_id, un prix, un solde… ne viennent jamais du corps ni de l'adresse. Et méfie-toi des « corrections » par liste noire (delete corps.role) : le prochain champ sensible passera.
  • Les routes d'administration vérifient le rôle côté serveur (403). Cacher le bouton dans la page ne protège rien.
  • La ressource d'un autre répond 404, pour ne pas révéler son existence.
  • La seule preuve, c'est le test avec deux comptes : ce que A a le droit de faire, B doit être incapable de le faire sur les données de A.

À retenir

  1. Authentification : qui es-tu ? Autorisation : as-tu le droit sur cette donnée ? Il faut les deux.
  2. IDOR : changer un numéro dans l'adresse suffit, si la requête ne vérifie pas le propriétaire.
  3. Chaque requête sur une ressource contient AND client_id = ?, avec l'id de la session. En lecture, en modification et en suppression.
  4. Le rôle et le propriétaire viennent de la session et de la base, jamais du client : liste blanche des champs modifiables.
  5. Teste toujours avec deux comptes : c'est la seule preuve d'isolation.

Exercices

Les fichiers sont dans exercices/m3-05/. Le serveur se lance avec node serveur.js (dans factures, port 3012). La base est en mémoire : chaque redémarrage repart des données de départ. Comptes : awa@exemple.ci / mangue-papaye-2026, kofi@exemple.ci / kedjenou-du-dimanche, admin@comptaplus.ci / compta-plus-admin-2026. Outils : node verifier.js (dans factures, 10 tests avec deux comptes étanches) et node audit-autorisations.js <dossier> (dans outils).

Exercice 1 · guidé

Entrer chez Kofi avec le compte d'Awa

  1. Lance le serveur. Dans un deuxième terminal, depuis exercices/m3-05/requetes, connecte Awa et regarde ses factures :
curl.exe -s -c cookies-awa.txt -X POST http://127.0.0.1:3012/api/connexion -H "Content-Type: application/json" --data "@connexion-awa.json"
curl.exe -s -b cookies-awa.txt http://127.0.0.1:3012/api/factures
  1. Toujours en tant qu'Awa, demande la facture n°3, puis marque-la comme payée :
curl.exe -s -b cookies-awa.txt http://127.0.0.1:3012/api/factures/3
curl.exe -si -b cookies-awa.txt -X PUT http://127.0.0.1:3012/api/factures/3 -H "Content-Type: application/json" --data "@statut-payee.json"
  1. Envoie un profil qui contient un rôle, puis ouvre l'administration :
curl.exe -s -b cookies-awa.txt -X PUT http://127.0.0.1:3012/api/moi -H "Content-Type: application/json" --data "@profil-avec-role.json"
curl.exe -si -b cookies-awa.txt http://127.0.0.1:3012/api/admin/factures
  1. Redémarre le serveur, puis lance node verifier.js et node audit-autorisations.js ../factures (depuis outils).
  2. Pour chaque ligne signalée par l'audit, réponds à une seule question : d'où vient l'id ? De l'adresse (le client le choisit) ou de la session ?

Résultat attendu : Awa voit, modifie, devient admin et ouvre l'administration. Le banc de test donne 5 échecs sur 10, l'audit 7 points, et tu sais lesquels sont de vraies failles.

Indices

Dans la réponse de la facture n°3, regarde le champ client_id : est-ce celui d'Awa ?

Correction
  • La facture n°3 s'affiche ("client_id": 2, 1 200 000 FCFA) : c'est celle de Kofi. Le PUT répond 200. Le profil revient avec "role": "admin", et l'administration répond 200.
  • L'audit signale 5 requêtes « par id seul ». Trois sont de vraies failles : la lecture, la modification et la suppression d'une facture, où l'id vient de l'adresse. Deux sont sûres : la lecture et la mise à jour de l'utilisateur lui-même, où l'id vient de la session.
  • Les deux autres points : { ...moi, ...corps } (la copie du corps entier) et la route /api/admin sans vérification de rôle.
Exercice 2 · semi-guidé

Faire corriger par Claude, et refuser les demi-mesures

  1. Copie le dossier factures dans un dossier de travail. Dans la copie, demande à Claude :
Corrige les droits d'accès de serveur.js :
- lire, modifier et supprimer une facture vérifient dans la requête
  SQL qu'elle appartient au client connecté (AND client_id = ?, avec
  l'id de la session) ; sinon 404 ;
- PUT /api/moi n'accepte que nom et telephone (liste blanche) ;
- GET /api/admin/factures répond 403 si le rôle n'est pas admin.
  1. Relance le serveur et node verifier.js : 10 sur 10 attendus.
  2. Relance l'audit : il signale encore des lignes. Justifie chacune.
  3. Relis le diff, en cherchant les demi-mesures.

Résultat attendu : 10 sur 10 au banc de test, chaque alerte restante justifiée, et un diff sans demi-mesure.

Indices

Une alerte qui reste sur WHERE id = ? est acceptable si cet id est moi.id, c'est-à-dire qu'il vient de la session.

Correction

Le code attendu est celui de la section « Exemple concret ». Les demi-mesures à refuser :

  • delete corps.role avant de copier le corps : c'est une liste noire. Demain, client_id ou un autre champ passera.
  • La propriété vérifiée pour GET, mais pas pour PUT et DELETE : le banc de test le montre aussitôt.
  • Un 403 « cette facture ne t'appartient pas » : ça révèle qu'elle existe. Préfère 404.
  • Le lien vers l'administration caché dans la page, sans vérification côté serveur.

Vérifier la propriété en JavaScript (if (facture.client_id !== moi.id)) après la lecture est acceptable, à condition de le faire partout. La mettre dans la requête SQL est plus sûr : impossible de l'oublier dans une seule branche.

Exercice 3 · libre

Le plan de test à deux comptes de ton projet

Dans un de tes projets (par exemple l'espace client de Royal Senteur), crée deux comptes de test, A et B. Liste toutes les routes qui contiennent un identifiant (commande, adresse, facture, panier, avis…). Pour chacune, essaie avec le compte B d'agir sur une donnée de A : lire, modifier, supprimer. Vérifie aussi ce que le formulaire de profil accepte, et chaque route d'administration avec un compte non administrateur.

Résultat attendu : un tableau (route, action, résultat avec le compte B, verdict), lancé aussi sur ton code avec audit-autorisations.js, et une demande de correction pour chaque faille.

Pistes
  • Pense aux routes « secondaires » : télécharger une facture en PDF, l'historique des commandes, les adresses de livraison enregistrées.
  • Dans les outils du navigateur (onglet Réseau), regarde les requêtes envoyées par ta page : chaque nombre dans une adresse est un candidat.
  • Pour le profil, ajoute un champ inattendu (role, id) à la requête, et regarde s'il est enregistré.
  • Teste uniquement sur ton site et avec tes propres comptes de test.

Teste-toi

1. Awa, connectée, remplace /api/factures/14 par /api/factures/15 et voit la facture d'un autre client. Quel est le problème ?

Le serveur sait très bien qui est Awa. Il oublie seulement de vérifier que la facture demandée est la sienne. Des numéros compliqués ralentiraient l'attaque, mais seule la vérification la rend impossible.

2. Pour empêcher qu'un client se donne le rôle admin, l'IA ajoute delete corps.role avant de copier le corps. Suffisant ?

Une liste noire doit penser à tout ce qui est dangereux, aujourd'hui et demain. Une liste blanche n'accepte que ce qui est prévu : nom et telephone, rien d'autre.

3. Awa demande la facture de Kofi. Pourquoi répondre 404 plutôt que 403 ?

Un 403 dit « elle existe, mais pas pour toi » : on pourrait ainsi découvrir combien de factures existent. Un 404 ne donne aucune information. Pour une route d'administration, dont tout le monde connaît l'existence, le 403 est approprié.
