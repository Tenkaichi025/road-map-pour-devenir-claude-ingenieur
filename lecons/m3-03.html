Leçon 3.3

Gérer les secrets et le .env

L'idée

Un secret, c'est tout ce qui donne un accès : une clé d'API (pour envoyer des SMS, encaisser un paiement, envoyer des e-mails), le mot de passe d'une base de données, le secret qui signe les sessions. Celui qui le possède peut agir et dépenser en ton nom.

Or le code est fait pour être copié : sur GitHub, chez un collègue, dans une conversation avec l'IA, dans des sauvegardes. Un secret écrit dans le code part avec lui. Et une fois commité, il reste pour toujours dans l'historique git, même si tu le retires au commit suivant.

La règle : le code ne contient que le nom du secret, et lit sa valeur dans l'environnement : process.env.CLE_API_SMS. En local, la valeur vit dans un fichier .env, que .gitignore interdit à git de prendre. En production, c'est l'hébergeur qui la fournit. Enfin, un fichier .env.example, lui commité, liste les noms attendus, sans les valeurs.

Exemple concret

La boutique de pagnes confirme chaque commande par SMS, grâce à un fournisseur fictif, « SMS CI ». Elle a besoin de deux secrets : la clé de l'API SMS, et le secret de session qui signe le cookie de commande. Voici ce que l'IA a écrit « juste pour tester » : 

// TODO : déplacer ça ailleurs plus tard
const CLE_API_SMS = "smsci_live_7d1f0c9a4b2e8d63f5a1c0b9e7d4a2f1";
const SECRET_SESSION = "boutique-treichville-2026";

console.log("Démarrage avec la clé SMS :", CLE_API_SMS);

Et à côté :

# .env.example
CLE_API_SMS=smsci_live_7d1f0c9a4b2e8d63f5a1c0b9e7d4a2f1
SECRET_SESSION=boutique-treichville-2026

# .gitignore
node_modules/

Cinq problèmes :

  • La clé est écrite dans le code. Le « TODO » ne protège rien : le code partira tel quel au prochain commit.
  • Le secret de session est un mot facile à deviner, et lui aussi écrit dans le code.
  • La clé est affichée dans les journaux : quiconque voit les journaux du serveur la récupère.
  • .env.example, qui est commité, contient les vraies valeurs.
  • .gitignore n'interdit pas .env : le jour où quelqu'un le crée, il partira avec git add ..

La version corrigée

const path = require("node:path");

// En local : les valeurs viennent du fichier .env (ignoré par git).
// En production : l'hébergeur fournit les variables, il n'y a pas de fichier .env.
try {
  process.loadEnvFile(path.join(__dirname, ".env"));
} catch {
  // pas de fichier .env : on compte sur les variables de l'hébergeur
}
const { CLE_API_SMS, SECRET_SESSION } = process.env;
if (!CLE_API_SMS || !SECRET_SESSION || SECRET_SESSION.length < 32) {
  console.error("Configuration incomplète : copie .env.example en .env et remplis-le.");
  process.exit(1);   // on refuse de démarrer, plutôt que de tourner avec un secret par défaut
}
# .env.example : commité, SANS valeurs
CLE_API_SMS=
SECRET_SESSION=

# .gitignore
node_modules/
.env
.env.*
!.env.example

.env.* couvre aussi .env.local ou .env.production, et !.env.example autorise l'exemple. Pour fabriquer un secret de session solide (long et aléatoire), une ligne suffit : 

node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"

process.loadEnvFile existe depuis Node 20.12. Avec une version plus ancienne, lance node --env-file=.env serveur.js, ou utilise le paquet dotenv.

Le piège de l'historique git

Imagine que la clé a été commitée, puis retirée au commit suivant. Le code actuel est propre… mais git garde chaque version de chaque fichier. Deux commandes suffisent pour la retrouver : 

git log -S "smsci_live" --oneline      # les commits où ce texte apparaît ou disparaît
git show 6a94162                       # le contenu exact de ce commit, clé comprise

Si le dépôt a été poussé sur GitHub, même quelques minutes, considère la clé comme publique. Des robots parcourent GitHub en permanence à la recherche de clés, et la clé a pu être copiée dans des clones, des forks ou des sauvegardes. Supprimer le dépôt ou réécrire l'historique n'efface pas ces copies.

La procédure de réaction, dans cet ordre

  1. Changer la clé chez le fournisseur, tout de suite. Dans son tableau de bord, révoque l'ancienne clé et crée-en une nouvelle. C'est la seule étape qui rend la clé publiée inutilisable : tout le reste vient après.
  2. Mettre la nouvelle clé dans .env (et chez l'hébergeur), puis redémarrer l'application.
  3. Regarder les journaux d'utilisation du fournisseur depuis la fuite : SMS envoyés, paiements, connexions inconnues.
  4. Retirer la clé du code, et compléter .gitignore et .env.example.
  5. Nettoyer l'historique avec git filter-repo (installation : python -m pip install git-filter-repo), puis git push --force, et prévenir les autres personnes du projet : elles devront récupérer le dépôt à nouveau. Cette étape empêche de nouvelles copies, mais ne rattrape pas celles déjà faites : c'est pour ça que l'étape 1 passe avant. 
# expressions.txt : une ligne par secret à effacer de tout l'historique
regex:smsci_live_[0-9a-f]{32}

git filter-repo --replace-text expressions.txt --force
# la clé devient « ***REMOVED*** » dans tous les commits

Sur GitHub, active aussi le secret scanning et la push protection du dépôt : GitHub bloque alors un envoi qui contient une clé de format connu.

Vérifier le travail de l'IA

Quand l'IA touche à une configuration, une clé ou un mot de passe :

  • Aucune valeur secrète dans le code, même « pour tester », même avec un TODO à côté.
  • Pas de secret par défaut : process.env.SECRET || "secret123" cache une configuration manquante. Le programme doit refuser de démarrer.
  • Les secrets ne sont jamais écrits dans les journaux : méfie-toi de console.log(process.env) et des messages de démarrage « pour vérifier ».
  • .env.example ne contient que des noms, avec des valeurs vides ou visiblement fictives.
  • .gitignore contient .env, .env.* et !.env.example. Vérifie-le avant le premier commit avec git check-ignore -v .env.
  • Un secret de session est long et aléatoire (crypto.randomBytes), jamais un mot ou une phrase.
  • Aucun secret dans le code envoyé au navigateur. Tout ce qui est dans le JavaScript de la page est public, y compris les variables VITE_… ou NEXT_PUBLIC_…. Un appel avec une clé privée passe toujours par ton serveur.
  • Ne colle jamais tes vraies clés dans une conversation avec une IA. Donne-lui le nom de la variable, pas sa valeur.
  • Avant de rendre un dépôt public : audit du dossier et de son historique.

À retenir

  1. Le code contient le nom du secret (process.env.CLE), jamais sa valeur.
  2. .env : les valeurs, ignoré par git. .env.example : les noms, sans valeurs, commité.
  3. Ce qui a été commité reste dans l'historique : git log -S le retrouve.
  4. Clé publiée : d'abord la changer chez le fournisseur. Nettoyer l'historique vient après.
  5. Tout ce qui est envoyé au navigateur est public : une clé privée reste sur le serveur.

Exercices

Les fichiers sont dans exercices/m3-03/. Toutes les clés sont fictives : le fournisseur « SMS CI » n'existe pas. Deux outils t'aident :

  • node audit-secrets.js <dossier> fouille le code, les fichiers .env, le .gitignore et l'historique git. Il affiche les secrets masqués.
  • node preparer-depot.js <dossier> crée un dépôt d'entraînement avec une clé oubliée dans l'historique.
Exercice 1 · guidé

Sortir les secrets du code de la boutique

  1. Copie le dossier exercices/m3-03/boutique-sms dans un dossier de travail, en dehors du cours (par exemple C:\exos\boutique-sms). Dans la copie, tape git init.
  2. Depuis exercices/m3-03/outils, audite ta copie : node audit-secrets.js C:\exos\boutique-sms. Note les alertes.
  3. Dans serveur.js, remplace les deux constantes et le console.log par la version corrigée de la leçon.
  4. Vide les valeurs de .env.example, et complète .gitignore.
  5. Lance node serveur.js : le serveur doit refuser de démarrer.
  6. Copie .env.example en .env. Mets une clé SMS inventée et un secret généré avec la commande de la leçon. Relance : le serveur démarre.
  7. Teste une commande : curl.exe -s -X POST http://localhost:3010/api/commande -H "Content-Type: application/json" --data "@commande.json".
  8. Vérifie que .env est ignoré : git check-ignore -v .env. Puis relance l'audit.

Résultat attendu : 5 alertes au départ, puis un serveur qui refuse de démarrer sans .env, une commande qui passe (201), .env ignoré par git, et « Aucune alerte » à la fin.

Indices

Pour copier un fichier dans PowerShell : Copy-Item .env.example .env.

git check-ignore -v .env n'affiche rien ? Alors .env n'est pas ignoré : relis ton .gitignore.

Correction
  • Les 5 alertes : la clé dans serveur.js, le secret de session dans serveur.js, .gitignore sans .env, et deux valeurs dans .env.example.
  • Sans .env : « Configuration incomplète… », et le programme s'arrête. C'est voulu : un serveur qui démarre avec un secret manquant ou par défaut est pire qu'un serveur arrêté.
  • git check-ignore -v .env affiche .gitignore:2:.env .env : la ligne 2 du .gitignore protège le fichier.
  • Dans le terminal du serveur, la clé n'apparaît plus qu'en partie (smsci_live_…), et le message de démarrage ne l'affiche plus.
Exercice 2 · semi-guidé

La clé oubliée dans l'historique

  1. Depuis exercices/m3-03/outils : node preparer-depot.js C:\exos\depot-fuite.
  2. Dans C:\exos\depot-fuite, regarde sms.js : la clé n'y est plus. Puis git log --oneline.
  3. Retrouve-la : git log -S "smsci_live" --oneline, puis git show suivi du plus ancien numéro de commit affiché.
  4. Lance l'audit sur ce dépôt.
  5. Demande à Claude : « J'ai commité une clé d'API SMS il y a deux commits, puis je l'ai retirée du code. Le dépôt est sur GitHub. Que dois-je faire ? » Compare sa réponse avec la procédure de la leçon : commence-t-il par changer la clé chez le fournisseur ?
  6. Nettoie l'historique avec git filter-repo (voir la leçon), puis relance git log -S et l'audit.

Résultat attendu : la clé retrouvée dans le commit « Ajoute l'envoi de SMS », une seule alerte d'audit (dans l'historique), une analyse critique de la réponse de Claude, puis plus aucune trace après le nettoyage.

Indices

git filter-repo lit un fichier de remplacements. Crée expressions.txt à côté du dépôt (pas dedans), avec une seule ligne : regex:smsci_live_[0-9a-f]{32}.

Si la commande git filter-repo est introuvable après l'installation, essaie python -m git_filter_repo à la place.

Correction
  • git log -S affiche deux commits : celui qui a ajouté la clé et celui qui l'a retirée. git show sur le plus ancien affiche la clé en clair.
  • L'audit : une alerte, « ajouté(e) dans le commit … Ajoute l'envoi de SMS ». Le code actuel est propre : seul l'historique la contient.
  • Une bonne réponse de Claude commence par « révoque et remplace la clé chez le fournisseur ». Si elle commence par réécrire l'historique, ou se contente de dire de supprimer le fichier, c'est incomplet : la clé a pu être copiée dès sa publication.
  • Après git filter-repo --replace-text expressions.txt --force, git log -S n'affiche plus rien, le premier commit contient ***REMOVED***, et l'audit ne donne plus aucune alerte.
Exercice 3 · libre

L'inventaire des secrets de ton projet

Lance l'audit sur un de tes projets (par exemple Royal Senteur) : le dossier et son historique. Puis dresse l'inventaire de ses secrets : leur nom, le service auquel ils donnent accès, et l'endroit où vit chacun (code, .env, hébergeur, navigateur). Vérifie .gitignore et .env.example. Si une clé est dans l'historique d'un dépôt qui a été public, applique la procédure, en commençant par l'étape 1.

Résultat attendu : un inventaire complet (nom, service, emplacement, verdict), et pour chaque problème la correction faite.

Pistes
  • Cherche aussi dans le code envoyé au navigateur : les fichiers construits (dossier dist ou build) et les variables VITE_… / NEXT_PUBLIC_….
  • Pense aux secrets qui ne ressemblent pas à des clés : mot de passe de la base de données, identifiants SMTP pour les e-mails, mot de passe de l'espace d'administration.
  • Chez ton hébergeur (Vercel, Netlify, un VPS…), repère où se règlent les variables d'environnement de production.

Teste-toi

1. Tu as commité une clé d'API, puis tu l'as retirée au commit suivant. Le dépôt est public depuis hier. Que fais-tu en premier ?

La clé a pu être copiée dès sa publication, par des robots qui surveillent GitHub. Seule sa révocation chez le fournisseur la rend inutile. Nettoyer l'historique et cacher le dépôt viennent ensuite : ils évitent de nouvelles copies, pas celles déjà faites.

2. Que doit contenir le fichier .env.example ?

.env.example est commité : il documente ce qu'il faut configurer. Chaque personne copie ce fichier en .env et y met ses propres valeurs, qui ne quittent jamais sa machine.

3. L'IA place la clé de l'API SMS dans le JavaScript de la page, pour appeler le fournisseur directement depuis le navigateur. Problème ?

N'importe quel visiteur peut lire le code de la page, minifié ou non (F12). Les préfixes VITE_ et NEXT_PUBLIC_ signifient justement « à envoyer au navigateur ». Une clé privée reste côté serveur.
