Leçon 2.2

Une API REST et le JSON

L'idée

Une API, c'est la liste des requêtes qu'un serveur accepte, avec ce qu'il répond à chacune. C'est un menu : la page web, une application mobile ou un autre serveur commandent dedans. Les données voyagent presque toujours en JSON, un format texte simple que tous les langages savent lire.

REST est une façon d'organiser ce menu. L'adresse désigne une chose (/api/evenements, ou /api/evenements/12 pour l'événement n°12). La méthode dit l'action : GET pour lire, POST pour créer, PUT pour modifier, DELETE pour supprimer.

Et de l'autre côté, la page qui appelle l'API doit prévoir que les données mettent du temps à arriver, qu'elles n'arrivent pas, ou qu'il n'y en a aucune. Un écran qui charge des données a donc toujours quatre états : chargement, erreur, vide, liste. L'IA n'en code souvent qu'un seul : celui où tout va bien.

Exemple concret

L'agenda des événements d'Abidjan : une API qui gère des concerts, des marchés, des ateliers, et une page qui les affiche. Voici un événement, en JSON : 

{
  "id": 1,
  "titre": "Nuit du coupé-décalé",
  "date": "2026-11-21",
  "lieu": "Palais de la Culture, Treichville",
  "places": 1200,
  "gratuit": false
}

Les règles du JSON

  • Les noms des champs sont toujours entre guillemets doubles : "titre", jamais titre ni 'titre'.
  • Valeurs possibles : du texte entre guillemets, un nombre (1200, sans guillemets), true, false, null, une liste [ ] ou un objet { }.
  • Pas de virgule après le dernier élément, et pas de commentaires.
  • Il n'y a pas de type « date » : on l'écrit en texte, au format AAAA-MM-JJ.

Les routes de l'API

RequêteRôleRéponse si tout va bien
GET /api/evenementsLire tous les événements200 + la liste
GET /api/evenements/1Lire l'événement n°1200 + l'événement
POST /api/evenementsCréer un événement201 + l'événement créé
PUT /api/evenements/1Remplacer l'événement n°1200 + l'événement modifié
DELETE /api/evenements/1Supprimer l'événement n°1204, sans contenu

Et si l'événement demandé n'existe pas : 404, pour GET, PUT et DELETE. Si les données envoyées sont invalides : 400.

Côté serveur : choisir ce qu'on garde

Quand un événement arrive, le serveur le vérifie champ par champ, puis il recopie uniquement les champs qu'il connaît. Jamais le corps reçu tel quel : 

async function lireEvenement(req) {
  let demande;
  try {
    demande = await lireCorps(req);
  } catch {
    return { erreur: "Le corps de la requête n'est pas du JSON valide." };
  }
  const probleme = verifier(demande);          // titre ? date au bon format ? places entier positif ?
  if (probleme) return { erreur: probleme };
  const { titre, date, lieu, places, gratuit } = demande;   // on ne garde que les champs connus
  return { evenement: { titre, date, lieu, places, gratuit } };
}

Pourquoi ? Si le serveur recopiait le corps entier, un client pourrait envoyer "id": 1 pour écraser un autre événement, ou "admin": true pour se donner des droits. C'est le serveur qui décide, pas le client.

Côté page : les quatre états

async function charger() {
  afficher("chargement");                      // 1. on prévient : ça arrive
  try {
    const reponse = await fetch("/api/evenements");
    if (!reponse.ok) throw new Error("Erreur " + reponse.status);   // 2. voir ci-dessous
    const evenements = await reponse.json();
    if (evenements.length === 0) return afficher("vide");           // 3. rien à montrer : on le dit
    afficher("liste", evenements);
  } catch {
    afficher("erreur");                        // 4. réseau coupé, serveur arrêté, réponse en erreur
  }
}

Le piège de la ligne 2 : fetch ne considère comme une erreur que l'échec du réseau. Un 404 ou un 500 est pour lui une réponse normale. Sans la vérification de reponse.ok, la page essaie d'afficher un message d'erreur du serveur comme si c'était une liste d'événements.

Vérifier le travail de l'IA

Les erreurs classiques d'une API générée par IA, et comment les débusquer :

  • Les adresses désignent des choses et les méthodes disent l'action : DELETE /api/evenements/12, pas GET /supprimerEvenement?id=12.
  • Création → 201, suppression → 204. Et un id inconnu donne 404 pour GET, PUT et DELETE : teste les trois.
  • Un corps vide {} ou un champ du mauvais type ("places": "beaucoup") est refusé avec 400.
  • Le serveur ne recopie jamais le corps tel quel. Test : envoie un "id" ou un "admin": true, et vérifie qu'ils sont ignorés.
  • PUT garde l'id de l'événement, et ne laisse pas un objet à moitié vide.
  • Les fonctions de vérification sont vraiment appelées. L'IA écrit parfois une belle fonction verifier()… que rien n'utilise. Cherche où elle est appelée.
  • Côté page : reponse.ok est vérifié, les quatre états existent, et les textes reçus sont affichés avec textContent.

À retenir

  1. Une API, c'est la liste des requêtes qu'un serveur accepte. Le JSON est le format des données échangées.
  2. REST : l'adresse désigne la chose, la méthode dit l'action (GET, POST, PUT, DELETE).
  3. Le serveur vérifie chaque champ et ne garde que ceux qu'il connaît. C'est lui qui décide, pas le client.
  4. fetch ne lève pas d'erreur sur un 404 ou un 500 : vérifie toujours reponse.ok.
  5. Un écran qui charge des données a quatre états : chargement, erreur, vide, liste.

Exercice 1 · guidé

Faire le tour de l'API, puis provoquer les quatre états

  1. Dans exercices/m2-02/api-evenements, lance node serveur.js. Ouvre http://localhost:3002 : la page affiche 3 événements. Ouvre aussi http://localhost:3002/api/evenements : c'est le JSON brut que la page reçoit.
  2. Dans un deuxième terminal, depuis requetes, crée un événement, puis recharge la page :
curl.exe -si -X POST http://localhost:3002/api/evenements -H "Content-Type: application/json" --data "@nouvel-evenement.json"
  1. Modifie l'événement n°1 : même commande avec -X PUT, l'adresse /api/evenements/1 et --data "@modif-evenement.json". Recharge la page.
  2. Supprime l'événement n°2 : curl.exe -si -X DELETE http://localhost:3002/api/evenements/2. Puis redemande-le avec GET.
  3. État « chargement » : F12, onglet Réseau, menu de limitation (« Aucune limitation ») → choisis une connexion lente (3G), puis recharge. Remets « Aucune limitation » ensuite.
  4. État « vide » : supprime tous les événements restants avec DELETE, puis recharge la page.
  5. État « erreur » : arrête le serveur (Ctrl + C). Dans la page encore ouverte, tape charger() dans la Console. Puis relance le serveur et clique sur « Réessayer ».

Résultat attendu : création → 201, modification → 200, suppression → 204, puis 404 sur l'événement supprimé. Tu as vu les quatre états de la page, et tu sais ce qui déclenche chacun.

Indices

Regarde les en-têtes de la réponse du POST : la ligne Location donne l'adresse du nouvel événement.

Après le redémarrage du serveur, la liste revient à ses 3 événements de départ : tout est en mémoire.

Correction
  • POST → 201 Created, avec l'id 4 et Location: /api/evenements/4.
  • PUT /api/evenements/1 → 200 OK : la date passe au 22 novembre et les places à 1500.
  • DELETE /api/evenements/2 → 204 No Content, sans corps. Le GET qui suit → 404.
  • Connexion lente : « Chargement des événements… » reste visible un moment.
  • Plus d'événements : « Aucun événement prévu pour le moment. »
  • Serveur arrêté : « Impossible de charger les événements. » et le bouton « Réessayer », qui fonctionne dès que le serveur est relancé.

Indices

Pour l'état « erreur », regarde aussi la Console : une erreur rouge non gérée veut dire que la page n'a rien prévu.

Correction

Les oublis habituels, quand on ne les demande pas :

  • Pas d'état « chargement » : l'écran reste blanc pendant l'attente.
  • Pas d'état « erreur » : serveur arrêté = écran blanc et erreur rouge dans la Console.
  • Pas d'état « vide » : une liste vide donne une page vide, sans explication.
  • reponse.ok non vérifié.
  • Les cartes construites avec innerHTML et ${evenement.titre} : le titre piégé ouvre une alerte. C'est la faille XSS (leçon 3.2).

Exemple de demande de correction :

Complète public/app.js :
1. Affiche « Chargement… » pendant la requête.
2. Si fetch échoue ou si reponse.ok est faux, affiche un message
   d'erreur et un bouton Réessayer.

La leçon : tes prompts doivent nommer les cas difficiles. L'IA code très bien le cas où tout va bien, et oublie volontiers le reste.

Exercice 3 · libre

Auditer une API générée par IA

exercices/m2-02/api-bugguee/ contient la même API, « améliorée » par une IA. Elle se lance avec node serveur.js, sur le port 3003. À première vue, tout marche. Elle contient pourtant au moins 5 problèmes.

Trouve-les avec curl.exe et les fichiers du dossier requetes. Pour chacun, écris un mini-rapport : la requête, la réponse attendue, la réponse obtenue. Ensuite, fais corriger l'API par Claude en lui donnant tes rapports, puis relance tous tes tests.

Résultat attendu : une liste d'au moins 5 problèmes, chacun prouvé par une requête, puis une API corrigée qui passe tous tes tests.

Pistes
  • Reprends la liste « Vérifier le travail de l'IA » et transforme chaque ligne en une requête de test.
  • Après chaque requête qui modifie quelque chose, relis toute la liste avec GET /api/evenements.
  • Essaie un id qui n'existe pas avec chaque méthode. Regarde bien ce qui reste dans la liste après un DELETE.
  • Lis le fichier : la fonction verifier existe. Où est-elle appelée ?
Correction
  1. POST répond 200 au lieu de 201.
  2. POST avec evenement-vide.json crée un événement qui n'a qu'un id : aucune vérification. La fonction verifier existe, mais n'est plus jamais appelée.
  3. POST avec evenement-piege.json crée un deuxième événement n°1, avec "admin": true : le corps est recopié tel quel.
  4. PUT avec modif-partielle.json remplace l'événement par { "lieu": … } : il perd son id, son titre, sa date.
  5. GET /api/evenements/99 répond 200 avec un corps vide, au lieu de 404.
  6. DELETE /api/evenements/99 répond 204… et supprime le dernier événement de la liste. La vérification « introuvable → 404 » a disparu. L'index vaut alors -1, et splice(-1, 1) retire le dernier élément.
  7. Bonus : json-casse.json fait planter le serveur (leçon 2.1).

Le problème 6 est le plus grave : une simple faute de frappe dans un id efface les données de quelqu'un d'autre, sans aucune erreur. Seul un test qui supprime un id inexistant puis relit la liste le révèle.

Teste-toi

1. Le serveur répond 404, mais le catch de ta fonction n'est jamais exécuté. Pourquoi ?

Pour fetch, un 404 ou un 500 est une réponse comme une autre. C'est à toi de tester reponse.ok (vrai pour les codes 200 à 299) et de traiter le reste comme une erreur.

2. Lequel de ces textes est du JSON valide ?

En JSON, les noms des champs sont toujours entre guillemets doubles, et il n'y a pas de virgule après le dernier élément. true s'écrit sans guillemets.

3. Dans une API REST, comment supprimer l'événement n°12 ?

L'adresse désigne la chose (l'événement 12), la méthode dit l'action (supprimer). Une suppression en GET est même dangereuse : un simple lien, ou un robot qui parcourt les pages, pourrait effacer des données.
