Leçon 2.1

Le cycle requête-réponse

L'idée

Tout le web fonctionne sur un seul échange, répété des milliards de fois : un client envoie une requête, un serveur renvoie une réponse. Le client, c'est ton navigateur, une application mobile, ou un outil en ligne de commande comme curl. Le serveur, c'est un programme qui attend des requêtes et décide quoi répondre.

Une requête dit ce qu'on veut faire (la méthode : GET pour lire, POST pour créer…) et sur quoi (le chemin : /reservations). Une réponse commence toujours par un code de statut : un nombre qui résume le résultat. 200, tout va bien. 404, ça n'existe pas. 500, le serveur a planté.

Pourquoi c'est essentiel avec l'IA ? Parce que l'IA écrit volontiers un serveur qui répond « 200 » à tout, même quand ça a échoué. Le code de statut est le premier mensonge à vérifier.

Exemple concret

Un système de réservation de salles de réunion. Trois salles : Baobab, Fromager et Iroko. On peut voir les salles, et en réserver une pour une date. Deux personnes ne doivent pas réserver la même salle le même jour.

Une requête, une réponse

Voici, mot pour mot, ce qui circule quand Awa réserve la salle Baobab :

POST /reservations HTTP/1.1                      ← méthode, chemin
Host: localhost:3000
Content-Type: application/json                   ← en-têtes : des infos sur la requête

{ "salle": "Baobab", "date": "2026-11-14", "nom": "Awa" }    ← le corps : les données envoyées
HTTP/1.1 201 Created                             ← le code de statut
Content-Type: application/json; charset=utf-8

{ "id": 1, "salle": "Baobab", "date": "2026-11-14", "nom": "Awa" }

Si Kofi envoie ensuite exactement la même demande, le serveur doit répondre autre chose : 

HTTP/1.1 409 Conflict

{ "erreur": "La salle Baobab est déjà réservée le 2026-11-14." }

Le code du serveur

Voici le cœur du serveur Node.js, écrit avec le module http fourni avec Node (aucune installation). Tu n'as pas à savoir l'écrire. Tu dois savoir le lire : quelle requête arrive, quelles vérifications sont faites, et quel code est renvoyé dans chaque cas. 

if (req.method === "POST" && url.pathname === "/reservations") {
  let demande;
  try {
    demande = await lireCorps(req);              // le corps envoyé par le client
  } catch {
    return repondre(res, 400, { erreur: "Le corps n'est pas du JSON valide." });
  }

  const { salle, date, nom } = demande || {};
  if (!salle || !date || !nom) {
    return repondre(res, 400, { erreur: "Il faut une salle, une date et un nom." });
  }
  if (!salles.includes(salle)) {
    return repondre(res, 404, { erreur: `La salle ${salle} n'existe pas.` });
  }
  if (reservations.some((r) => r.salle === salle && r.date === date)) {
    return repondre(res, 409, { erreur: `La salle ${salle} est déjà réservée le ${date}.` });
  }

  const reservation = { id: reservations.length + 1, salle, date, nom };
  reservations.push(reservation);
  return repondre(res, 201, reservation);       // tout est bon : créé
}

Remarque la forme : chaque vérification qui échoue s'arrête tout de suite avec un return et un code d'erreur précis. On n'arrive à la création qu'après avoir tout vérifié.

Les codes que tu verras le plus

  • 200 OK : la demande a réussi (lecture, modification).
  • 201 Created : quelque chose a été créé.
  • 400 Bad Request : la demande est mal formée ou incomplète. C'est la faute du client.
  • 401 / 403 : pas connecté / pas le droit (leçon 2.4 et module 3).
  • 404 Not Found : ce qui est demandé n'existe pas.
  • 409 Conflict : la demande entre en conflit avec l'état actuel (déjà réservé).
  • 500 Internal Server Error : le serveur a planté. C'est la faute du serveur.

Retiens la règle : 4xx, c'est le client qui s'est trompé. 5xx, c'est le serveur.

Vérifier le travail de l'IA

Quand l'IA écrit ou modifie du code serveur :

  • Chaque cas renvoie le bon code : 201 pour une création, 400 pour une demande invalide, 404 pour ce qui n'existe pas, 409 pour un conflit. Pas 200 partout.
  • Teste avec curl -si et regarde la première ligne (le code), pas seulement le contenu.
  • Le serveur vérifie tout ce qui arrive : champs présents, valeurs autorisées. Il ne fait jamais confiance au client.
  • Un JSON mal formé donne une réponse 400, pas un plantage. Test : envoie un fichier cassé, puis vérifie que le serveur répond encore.
  • Après chaque réponse d'erreur dans une condition, il y a un return. Sinon le code continue et fait quand même l'action.
  • Les messages d'erreur sont clairs pour l'utilisateur, sans détails internes (chemins de fichiers, traces d'erreur).

À retenir

  1. Le client envoie une requête : une méthode, un chemin, des en-têtes, parfois un corps.
  2. Le serveur renvoie une réponse qui commence toujours par un code de statut.
  3. GET pour lire, POST pour créer. 4xx : erreur du client. 5xx : erreur du serveur.
  4. Un bon serveur vérifie tout, et s'arrête au premier problème avec le code qui le décrit.
  5. Teste avec curl -si : le code de statut ne ment pas, le texte peut mentir.

Exercice 1 · guidé

Parler au serveur de réservation

  1. Ouvre un terminal dans exercices/m2-01/serveur-salles et lance : 
    node serveur.js
    Le message Serveur prêt : http://localhost:3000/salles s'affiche. Laisse ce terminal ouvert : le serveur tourne tant qu'il est ouvert.
  2. Dans ton navigateur, ouvre http://localhost:3000/salles. Puis F12, onglet Réseau, recharge, et clique sur la ligne salles : tu vois la méthode, le code de statut et les en-têtes.
  3. Ouvre un deuxième terminal dans exercices/m2-01/requetes. Lis la liste des salles :
curl.exe -si http://localhost:3000/salles
  1. Réserve la salle Baobab pour Awa (le corps est lu dans le fichier reservation-awa.json) :
curl.exe -si -X POST http://localhost:3000/reservations -H "Content-Type: application/json" --data "@reservation-awa.json"
  1. Envoie maintenant la demande de Kofi : --data "@reservation-kofi.json". Puis une demande incomplète : --data "@reservation-incomplete.json".
  2. Demande une adresse qui n'existe pas : curl.exe -si http://localhost:3000/salles/zzz.
  3. Regarde le premier terminal : chaque requête reçue par le serveur y est écrite.
  4. Arrête le serveur avec Ctrl + C, relance-le, et redemande /reservations.

Résultat attendu : tu obtiens dans l'ordre 200, 201, 409, 400 et 404, et tu sais expliquer chaque code. Après le redémarrage, la liste des réservations est vide.

Indices

Échec de la connexion ou Connection refused ? Le serveur ne tourne pas : regarde le premier terminal. Couldn't read data from file ? Ton deuxième terminal n'est pas dans le dossier requetes.

L'option -i affiche les en-têtes de la réponse, dont la première ligne avec le code. -s cache la barre de progression.

Correction
  1. 200 OK : lecture réussie, la liste des 3 salles.
  2. 201 Created : la réservation d'Awa est créée, avec l'id 1.
  3. 409 Conflict : Kofi demande la même salle à la même date.
  4. 400 Bad Request : il manque la date et le nom.
  5. 404 Not Found : aucune route ne correspond à /salles/zzz.

Après le redémarrage, tout a disparu : les réservations sont gardées en mémoire, dans une simple liste JavaScript. Pour les garder, il faut une base de données : c'est la leçon 2.3.

Exercice 3 · libre

La double réservation

Le serveur exercices/m2-01/serveur-double/ a été « amélioré » par une IA. Depuis, Awa et Kofi peuvent réserver la même salle le même jour : les deux reçoivent un 201. Reproduis le problème avec curl.exe, trouve la cause, corrige-la, puis prouve que c'est réparé.

Résultat attendu : Awa reçoit 201, Kofi reçoit 409, et GET /reservations ne contient qu'une seule réservation.

Pistes
  • Commence par reproduire : deux requêtes, deux codes, puis la liste des réservations.
  • Le serveur a bien une vérification de conflit. Pourquoi ne trouve-t-elle jamais rien ? Ajoute un console.log juste avant, pour voir ce que contient la liste.
  • Compare, lettre par lettre, les noms des champs d'une réservation enregistrée avec ceux utilisés dans la vérification.
Correction

Ligne 58, la vérification compare r.jour === date. Mais les réservations sont enregistrées avec un champ date, pas jour. r.jour vaut toujours undefined, donc le conflit n'est jamais détecté. Correction : 

if (reservations.some((r) => r.salle === salle && r.date === date)) {

C'est le même genre de bug qu'en 1.5 (temperature au lieu de temp). Ici, il n'y a aucune erreur nulle part : seul un test qui envoie deux fois la même demande et attend un 409 le révèle. Garde ce réflexe : pour chaque règle métier (« pas deux réservations en même temps »), il faut un test qui essaie de la violer.

Teste-toi

1. Tu envoies une réservation sans date. Quel code le serveur doit-il renvoyer ?

La demande est incomplète : c'est une erreur du client, donc un code 4xx, ici 400. 500 voudrait dire que le serveur lui-même a planté. Et 200 avec une erreur dans le corps trompe tous les outils qui se fient au code.

2. Quelle est la différence entre GET et POST ?

La méthode dit l'intention. POST n'est pas plus sûr : sans HTTPS, son corps circule en clair exactement comme une adresse GET (module 3).

3. Le serveur généré par l'IA plante quand on lui envoie un JSON mal formé. Que dois-tu exiger ?

Le serveur ne contrôle pas ce que les clients envoient : n'importe qui peut lui écrire avec curl. Il doit donc se défendre lui-même. Un redémarrage automatique cache le problème, et un attaquant pourrait le faire planter en boucle.
