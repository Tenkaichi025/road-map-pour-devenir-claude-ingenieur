Leçon 1.4

JavaScript et le DOM

L'idée

Le fichier HTML n'est que le plan de départ. Une fois qu'il l'a lu, le navigateur en fait le DOM : un arbre d'objets gardé en mémoire, qui représente la page vivante. Chaque balise devient un objet que JavaScript peut lire et modifier : ajouter un élément, changer un texte, cacher un bloc.

JavaScript agit en réponse à des événements : un clic, une touche pressée, l'envoi d'un formulaire. Et retiens bien ceci : JavaScript modifie le DOM, jamais le fichier HTML. Recharge la page, et tout ce qu'il a ajouté disparaît, sauf si tu l'as sauvegardé quelque part.

Exemple concret

Une liste de tâches. Le HTML prévoit un formulaire et une liste vide :

<form id="form-tache">
  <label for="nouvelle">Nouvelle tâche</label>
  <input id="nouvelle" name="nouvelle" required>
  <button type="submit">Ajouter</button>
</form>
<ul id="liste"></ul>

Le JavaScript fait toujours les mêmes 5 gestes :

// 1. Trouver les éléments
const form = document.querySelector("#form-tache");
const champ = document.querySelector("#nouvelle");
const liste = document.querySelector("#liste");

// 2. Écouter un événement
form.addEventListener("submit", (evenement) => {
  evenement.preventDefault();          // empêche la page de se recharger

  const li = document.createElement("li");   // 3. Créer un élément
  li.textContent = champ.value;              // 4. Y mettre du texte
  liste.append(li);                          // 5. L'accrocher dans le DOM

  champ.value = "";
});

Tu n'as pas besoin de savoir l'écrire de mémoire. Tu dois savoir le lire : où on cherche les éléments, quel événement on écoute, ce qu'on modifie.

Le piège de innerHTML

L'IA écrit souvent ceci à la place de l'étape 4 :

li.innerHTML = champ.value;   // DANGER

textContent affiche le texte tel quel. innerHTML, lui, le lit comme du HTML. Si quelqu'un tape <img src=x onerror="alert('piraté')">, le navigateur exécute le code. C'est une faille appelée XSS (on l'étudie en détail à la leçon 3.2). Règle simple : du texte venant d'un utilisateur passe toujours par textContent.

Code source ou DOM ?

Ctrl + U affiche le code source : le fichier HTML d'origine, celui qui a été téléchargé. L'onglet Éléments des outils montre le DOM : la page telle qu'elle est maintenant, avec tout ce que JavaScript a ajouté. Quand tu cherches un bug d'affichage, c'est le DOM qu'il faut regarder.

Vérifier le travail de l'IA

Quand l'IA ajoute ou modifie du JavaScript :

  • Le texte saisi par un utilisateur est inséré avec textContent, jamais avec innerHTML.
  • Un formulaire géré en JavaScript appelle preventDefault(), sinon la page se recharge.
  • Le script est chargé avec defer, ou placé après les éléments qu'il utilise.
  • La Console reste vide après chaque action : ajouter, supprimer, recharger.
  • Teste les cas limites : champ vide, texte très long, caractères spéciaux (< > " é).
  • L'IA n'a modifié que ce que tu as demandé. Tu le vérifies avec git diff (exercice 2).
  • Si les données doivent survivre au rechargement, elles sont sauvegardées, et tu l'as testé en rechargeant.

À retenir

  1. Le DOM est la version vivante de la page. JavaScript modifie le DOM, pas le fichier HTML.
  2. Toujours le même schéma : trouver un élément, écouter un événement, modifier le DOM.
  3. textContent pour du texte. innerHTML avec du texte d'utilisateur = faille.
  4. Tout ce que JavaScript ajoute disparaît au rechargement, sauf si c'est sauvegardé.
  5. Après chaque modification de l'IA : relis le diff, puis teste les cas limites.

Exercice 1 · guidé

Suivre un clic jusqu'au DOM

  1. Ouvre exercices/m1-04/taches/app.js dans ton éditeur. Juste après la ligne evenement.preventDefault();, ajoute : 
    console.log("Tâche ajoutée :", champ.value);
  2. Ouvre la page dans le navigateur, puis F12 et l'onglet Console.
  3. Ajoute trois tâches. Chaque ajout affiche une ligne dans la Console.
  4. Passe dans l'onglet Éléments et déplie <ul id="liste">. Ajoute une quatrième tâche en regardant l'arbre : le nouveau <li> apparaît et clignote.
  5. Appuie sur Ctrl + U pour voir le code source. Cherche <ul id="liste">.

Résultat attendu : les logs dans la Console, les <li> visibles dans Éléments, et une liste vide dans le code source. Tu sais expliquer pourquoi.

Indices

Rien dans la Console ? As-tu enregistré app.js puis rechargé la page ?

Correction

Le code source montre le fichier tel qu'il a été téléchargé : la liste y est vide. Les <li> n'existent que dans le DOM, en mémoire, parce que JavaScript les y a ajoutés. Recharge la page : ils disparaissent.

console.log est ton premier outil de diagnostic : il te montre ce que contient une variable à un moment précis. Pense à retirer ces lignes quand tu as fini.

Exercice 2 · semi-guidé

Faire ajouter « Supprimer » et relire le diff

  1. Copie le dossier taches en dehors du projet, par exemple dans Documents/exos/taches. Ouvre un terminal dans cette copie et tape : 
    git init
git add .
git commit -m "Version de départ"
    Tu viens de prendre une photo du code avant que l'IA y touche (Git en détail : leçon 4.1).
  2. Ouvre Claude Code dans ce dossier et demande :
Dans app.js, ajoute un bouton « Supprimer » à chaque tâche.
Un clic supprime uniquement cette tâche. Ne modifie rien
d'autre que ce qui est nécessaire.
  1. Tape git diff dans le terminal. Les lignes en + ont été ajoutées, celles en - supprimées. Lis chaque ligne.
  2. Teste : ajoute 3 tâches et supprime celle du milieu. Ajoute la tâche <b>gras</b>. Elle doit s'afficher telle quelle, sans être mise en gras.

Résultat attendu : la bonne tâche est supprimée, <b>gras</b> s'affiche en texte brut, le diff ne touche que ce qui est nécessaire, et la Console est vide.

Indices

Dans le diff, cherche innerHTML, et vérifie que preventDefault n'a pas disparu.

Le bouton Supprimer doit être un <button type="button">. Sans type="button", un bouton placé dans un formulaire l'envoie.

Correction

Un bon diff ressemble à ceci :

   li.textContent = champ.value;
+  const supprimer = document.createElement("button");
+  supprimer.type = "button";
+  supprimer.textContent = "Supprimer";
+  supprimer.addEventListener("click", () => li.remove());
+  li.append(supprimer);
   liste.append(li);

Signaux d'alerte à refuser :

  • li.innerHTML = `${champ.value} <button>Supprimer</button>` : c'est la faille XSS. Le test <b>gras</b> l'aurait révélée.
  • Tout le fichier a été réécrit alors qu'on demandait un ajout.
  • Une suppression par position (liste.children[2]) qui retire la mauvaise tâche après une première suppression.

Si le résultat ne te plaît pas, git checkout -- app.js remet le fichier comme sur la photo.

Exercice 3 · libre

« Mes tâches disparaissent quand je recharge »

Dans ta copie, fais en sorte que les tâches survivent au rechargement, en les enregistrant dans le localStorage (un petit espace de stockage du navigateur). Tu peux faire écrire le code par Claude. Mais c'est toi qui définis et passes les tests qui prouvent que ça marche.

Résultat attendu : une liste de tests écrite par toi, tous réussis, et un diff relu.

Pistes
  • Les données sont visibles dans F12, onglet Application, puis Local Storage. Ce site de cours range ta progression exactement là.
  • Pense à tout ce qui modifie la liste : ajouter, mais aussi supprimer.
  • Que se passe-t-il si la valeur enregistrée est abîmée ? Modifie-la toi-même dans l'onglet Application (remplace-la par abc), puis recharge.
Correction

Les tests à passer :

  1. Ajouter 2 tâches, recharger : elles sont toujours là.
  2. En supprimer une, recharger : elle ne revient pas.
  3. Fermer l'onglet, rouvrir la page : les tâches sont là.
  4. Remplacer la valeur par abc dans Application, recharger : la page s'affiche quand même (une liste vide), sans erreur rouge.
  5. <b>gras</b> s'affiche toujours en texte brut après un rechargement.

Le test 4 est celui que l'IA oublie le plus. La lecture doit être protégée :

function lire() {
  try {
    return JSON.parse(localStorage.getItem("taches")) || [];
  } catch {
    return [];   // valeur abîmée : on repart d'une liste vide au lieu de planter
  }
}

Teste-toi

1. Tu ajoutes 3 tâches, puis tu ouvres le code source (Ctrl + U). La liste est vide. Pourquoi ?

JavaScript ne réécrit jamais le fichier HTML. Il modifie le DOM. Pour voir la page réelle, utilise l'onglet Éléments.

2. L'IA a écrit li.innerHTML = champ.value;. Quel est le risque ?

innerHTML interprète le texte comme du HTML. C'est la porte d'entrée de la faille XSS. textContent affiche le texte tel quel, sans danger.

3. À chaque ajout, la page se recharge et la tâche disparaît aussitôt. Qu'est-ce qui manque ?

Par défaut, envoyer un formulaire charge une nouvelle page. preventDefault() annule ce comportement, pour que JavaScript s'occupe de tout.
