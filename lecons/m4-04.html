Leçon 4.4

Relire et challenger le code

L'idée

Quand tu fusionnes le code de l'IA, c'est ta signature qui est dessous. Si la boutique vend des sacs qu'elle n'a plus en stock, ce n'est pas « la faute de Claude ». L'ingénieur n'est donc pas un tampon d'approbation : la relecture est un acte de pilotage et de responsabilité.

Mais on ne relit pas un diff comme un roman, ligne après ligne, jusqu'à l'épuisement. On le relit comme un enquêteur : avec des questions précises. Les invariants tiennent-ils encore (ce qui doit toujours être vrai) ? Y a-t-il des effets de bord (une modification qui touche autre chose que prévu) ? Et la complexité a-t-elle dérivé (plus de code, de dépendances, de couches que le besoin n'en demande) ?

Et quand quelque chose te semble bizarre, tu challenges l'IA. Non pas « est-ce que c'est bon ? » : elle répondra oui. Tu lui demandes de prouver, de justifier et de révéler ses compromis.

Exemple concret

Le module de panier d'une boutique. Le ticket #42 demande une seule chose : « le client doit pouvoir changer la quantité d'un article, ou le retirer en mettant 0 ; ajouter modifierQuantite ». L'IA livre sa branche. Avec lodash installé, les 7 tests sont verts. Voici la relecture.

La stratégie : du plus révélateur au plus long

  1. La demande d'abord : relis le ticket. Tu ne peux pas juger un diff sans savoir ce qu'il devait faire.
  2. Le périmètre : git diff main --stat.
  3. Les tests et les dépendances : git diff main -- tests/ package.json. Ce qui a été retiré en dit souvent plus que ce qui a été ajouté.
  4. Le code, par ordre de risque : les entrées, les invariants, les effets de bord. Le reste en dernier.

Ce que la relecture trouve

// 1. Le stock n'est plus vérifié à l'ajout (et son test a disparu)
// Le stock est vérifié au moment du paiement, inutile de le faire ici.

// 2. « Gère tout » : modifierQuantite modifie le panier REÇU, et ne valide rien
function modifierQuantite(panier, reference, quantite) {
  const ligne = panier.find((l) => l.reference === reference);
  if (!ligne) return panier;                       // article absent : ignoré en silence
  if (quantite == 0) {                             // == : la chaîne "0" passe aussi
    panier.splice(panier.indexOf(ligne), 1);       // effet de bord
    return panier;
  }
  ligne.quantite = quantite;                       // -5, "2", 1.5, 500… tout passe
  return panier;
}

// 3. totalPanier renommé calculerTotal (et commande.js modifié en conséquence), avec lodash
function calculerTotal(panier) {
  return _.sumBy(panier, (ligne) => CATALOGUE[ligne.reference].prix * ligne.quantite);
}

Mis à l'épreuve, ce code ne tient qu'un invariant sur onze. Une quantité de -5 donne un total négatif (la boutique doit de l'argent au client), on commande 5 sacs alors qu'il en reste 3, et l'écran qui affiche le panier voit celui-ci changer « tout seul », puisque l'objet reçu est modifié. Les tests verts ne montraient rien de tout ça : l'IA n'avait testé que les cas qui marchent, et avait supprimé le test du stock.

1. PérimètreChaque fichier et chaque changement viennent-ils de la demande ?Non : renommage, commande.js, stock retiré.
2. DépendancesUne nouvelle bibliothèque, pour quel besoin réel ?lodash pour une somme qu'un reduce faisait déjà.

Verdict : refuser. Ce n'est pas une correction de détail, il faut repartir de main. La bonne version tient en six lignes, et réutilise la règle qui existait déjà :

// Change la quantité d'un article déjà dans le panier ; 0 le retire. Renvoie un NOUVEAU panier.
function modifierQuantite(panier, reference, quantite) {
  if (!panier.some((ligne) => ligne.reference === reference)) throw new Error(`Cet article n'est pas dans le panier : ${reference}`);
  if (quantite === 0) return panier.filter((ligne) => ligne.reference !== reference);
  verifierQuantite(reference, quantite);   // les mêmes règles qu'à l'ajout : entier, au moins 1, dans le stock
  return panier.map((ligne) => (ligne.reference === reference ? { ...ligne, quantite } : ligne));
}

Challenger l'IA : des prompts qui forcent la vérité

Explique ce diff fichier par fichier : pour chaque changement, quelle phrase
du ticket le justifie ? Si aucune, dis-le.

Liste les invariants de ce module (lis l'en-tête de src/panier.js) et montre,
pour chacun, la ligne de ton code qui le garantit, ou admets qu'aucune ne le fait.

Quels compromis as-tu faits ? Qu'est-ce qui pourrait casser chez un client ?

Joue l'avocat du diable : trouve trois failles dans ton propre code, avec pour
chacune un appel de fonction qui les prouve.

Propose la version la plus simple qui répond au ticket. Qu'as-tu ajouté
qui n'était pas demandé ?

Attention à la complaisance : face à une remarque, l'IA a tendance à te donner raison, même quand tu as tort. Ne te contente donc jamais d'un « vous avez raison, je corrige ». Exige une preuve : une ligne de code, un test qui échoue, un appel qui montre le problème.

Vérifier le travail de l'IA

La relecture elle-même a ses pièges :

  • Tu as relu la demande avant le diff, et tu sais dire ce qu'il devait faire en une phrase.
  • Tu as lu le --stat, les tests et package.json avant de te plonger dans le code.
  • Pour chaque fonction modifiée ou renommée, tu as cherché ses autres usages (Ctrl + Maj + F). Un renommage peut casser du code ailleurs, ou en modifier en silence.
  • Tu as écrit noir sur blanc les invariants du module, et vérifié chacun, pas seulement « ça a l'air bon ».
  • Tu as cherché les effets de bord : un objet reçu modifié (push, splice, une affectation sur un paramètre), un état partagé.
  • Tu ne t'es pas contenté d'un « vous avez raison » de l'IA : chaque correction est prouvée par un test ou un appel.
  • Tu as osé refuser un diff trop éloigné de la demande, plutôt que de le rafistoler point par point.

À retenir

  1. Tu signes ce que tu fusionnes : la relecture est du pilotage, pas un tampon.
  2. L'ordre : la demande, le --stat, les tests et les dépendances, puis le code par ordre de risque.
  3. On traque trois choses : les invariants cassés, les effets de bord, la complexité qui dérive.
  4. La grille : périmètre, dépendances, sécurité et invariants, tests, lisibilité. Puis accepter, corriger ou refuser.
  5. Challenger l'IA, c'est exiger des preuves (une ligne, un test, un appel), pas des promesses.

Indices

Dans ton prompt, cite l'en-tête des invariants et la fonction verifierQuantite. Ajoute « ne modifie que src/panier.js et tests/panier.test.js ; aucun test existant modifié ».

La fonction attendue est celle de la section « Exemple concret » (six lignes). Pendant le challenge, sois attentif :

Teste-toi

1. L'IA te livre un diff de 300 lignes. Par quoi commences-tu ?

La demande dit ce qu'on attendait, le --stat montre si le périmètre a été respecté, et les tests retirés ou modifiés signalent les problèmes les plus graves. Des tests verts ne prouvent pas que les bons cas sont testés.

2. Tu demandes à Claude « Ton code est-il correct ? ». Il répond « Oui ». Quelle meilleure question poser ?

Une question fermée obtient une réponse rassurante. Une question qui exige une preuve précise oblige l'IA à confronter son code aux règles, et révèle les trous.

3. modifierQuantite modifie le tableau reçu au lieu d'en renvoyer un nouveau. Pourquoi est-ce un problème ?

L'en-tête du module promettait que les fonctions ne modifient jamais le panier reçu. Les autres parties du code s'appuient sur cette promesse : la briser crée des bugs ailleurs, difficiles à retrouver.
