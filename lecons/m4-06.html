Ingénieur Claude Le parcours

Leçon 4.6

Créer tes propres skills

L'idée

Depuis le début du parcours, tu répètes les mêmes consignes : « lance les audits », « relis avec la grille », « écris les tests d'après les règles, pas d'après le code ». Tu les retapes dans chaque prompt, et tu en oublies toujours une.

Un skill règle ça. C'est un dossier qui contient un fichier SKILL.md (ta méthode, écrite une fois) et, si besoin, des scripts. Claude Code le charge quand il en a besoin : tu l'appelles avec /nom, ou Claude le déclenche seul quand ta demande correspond. Tes grilles et tes outils deviennent des réflexes permanents.

Mais un skill, c'est des consignes et du code que l'IA exécute. Il se teste, se relit et se versionne comme le reste. Nos essais réels l'ont montré : une consigne peut être ignorée, un script fait toujours la même chose.

Exemple concret

Le site de rendez-vous d'un salon de coiffure, avec des failles à trouver, et une branche écrite par l'IA à relire. On y construit 3 skills avec les outils des leçons précédentes. Tous les résultats cités ici viennent d'essais réels (octobre 2026, Claude Code 2.1, avec Haiku, le plus petit modèle).

Anatomie d'un SKILL.md

Un skill vit dans un dossier qui porte son nom. Deux emplacements possibles :

  • .claude/skills/<nom>/SKILL.md dans un projet : versionné avec git, partagé avec le projet.
  • ~/.claude/skills/<nom>/SKILL.md pour toi seul, dans tous tes projets (sous Windows : C:\Users\<toi>\.claude\skills\).
---
name: mon-skill
description: Ce que fait le skill. Utilise ce skill quand…
---

# Les consignes, en Markdown

1. Lance `node "${CLAUDE_SKILL_DIR}/scripts/outil.js" $ARGUMENTS`
2. …

Entre les deux lignes ---, l'en-tête (au format YAML : des lignes « clé: valeur »). En dessous, le corps : la méthode, en Markdown.

  • name : minuscules, chiffres et tirets. C'est aussi la commande : /mon-skill.
  • description : la ligne la plus importante. Elle dit ce que fait le skill et quand l'utiliser. C'est tout ce que Claude lit pour décider de s'en servir.
  • argument-hint : l'aide affichée quand tu tapes /mon-skill.
  • allowed-tools : les outils que Claude peut utiliser sans te demander pendant le skill. Bash(node:*) autorise seulement les commandes qui commencent par node.
  • disable-model-invocation: true : seul toi peux déclencher le skill (avec /nom), jamais Claude de lui-même.
  • Dans le corps, $ARGUMENTS est remplacé par ce que tu tapes après /nom, et ${CLAUDE_SKILL_DIR} par le chemin du dossier du skill. Ainsi, les scripts sont trouvés quel que soit le projet.

Atelier 1 — Le skill « audit-securite » (module 3)

Les 5 outils d'audit du module 3 vont dans .claude/skills/audit-securite/scripts/. Le SKILL.md dit comment s'en servir, et surtout comment juger leurs résultats : 

---
name: audit-securite
description: Audit de sécurité d'un projet web ENTIER, pas seulement des changements en cours (injection SQL, XSS, secrets et historique git, HTTPS, droits d'accès), avec 5 scripts de tri puis une vérification ligne par ligne. Utilise ce skill quand on demande si un site est sûr, avant une mise en ligne, ou pour auditer tout un projet.
argument-hint: "[dossier à auditer, la racine du projet par défaut]"
allowed-tools: Read, Grep, Glob, Bash(node:*)
---

# Audit de sécurité

Dossier à auditer : $ARGUMENTS (si rien n'est précisé : `.`, la racine du projet).

## Étapes
1. Lance ces 5 commandes telles quelles, une par une (le terminal est déjà à la racine du projet : n'ajoute pas de `cd` devant) :
   - `node "${CLAUDE_SKILL_DIR}/scripts/audit-sql.js" <dossier>`
   - `node "${CLAUDE_SKILL_DIR}/scripts/audit-xss.js" <dossier>`
   - `node "${CLAUDE_SKILL_DIR}/scripts/audit-https.js" <dossier>`
   - `node "${CLAUDE_SKILL_DIR}/scripts/audit-autorisations.js" <dossier>`
   - `node "${CLAUDE_SKILL_DIR}/scripts/audit-secrets.js" .` (toujours la racine : il vérifie le .gitignore et l'historique git)
2. Si une commande est refusée ou bloquée, relance-la. Si elle reste impossible, note « non lancé » : n'en conclus rien sur le code.
3. Les scripts ne font qu'un premier tri. Pour CHAQUE ligne signalée, ouvre le fichier : confirme la faille ou écarte-la, en une phrase.
4. Cherche ensuite ce que les scripts ne voient pas : requête construite sur plusieurs lignes, route sans vérification de session, propriétaire jamais vérifié.

## Règles
- Défensif uniquement. Aucune charge d'attaque, ni dans tes commandes, ni dans le rapport : décris ce qu'une personne pourrait obtenir, jamais comment.
- Pour prouver une faille, un marqueur inoffensif seulement (`<b>test</b>`, une apostrophe).
- Ne recopie jamais un secret : affiche-le masqué.
- Ne corrige rien pendant l'audit. Le rapport d'abord, les corrections après accord.

## Rapport attendu
1. Les 5 scripts : lancé ou non lancé, et le nombre de lignes signalées.
2. Un tableau : fichier:ligne | catégorie | confirmé ou faux positif | correction proposée.
3. Les 3 corrections prioritaires, la plus grave en premier.

Chaque ligne de ce fichier vient d'un essai raté :

  • La description. Première version : « Audit de sécurité défensif d'un projet web… ». À la question « Je mets le site en ligne demain. Est-ce qu'il est sûr ? », Claude a choisi un autre skill installé (security-review, prévu pour les changements en cours), et a raté 3 problèmes sur 6. Avec « un projet web ENTIER, pas seulement des changements en cours », il a choisi le bon.
  • « Lancé ou non lancé ». Une commande a été bloquée (par un contrôle de l'environnement, un « hook »). Claude n'a pas relancé le script, puis il a écrit : « les scripts ont manqué l'injection SQL ». Faux : le script n'avait jamais tourné. D'où l'étape 2 et le tableau en tête du rapport.
  • « N'ajoute pas de cd devant ». Claude écrivait cd … ; node …. Dans PowerShell, une commande qui change de dossier demande toujours ton autorisation : en mode automatique, les 5 ont été refusées.
  • Les règles ignorées. Malgré « Ne recopie jamais un secret » et « Aucune charge d'attaque », Haiku a recopié la clé en clair dans son rapport et décrit une attaque. Les consignes ne suffisent pas : c'est audit-secrets.js qui masque toujours la clé, parce que c'est écrit dans son code. Ton rôle reste de relire le rapport.

Atelier 2 — Le skill « relecture-pr » (grille de la leçon 4.4)

---
name: relecture-pr
description: Relit une branche produite par l'IA avec la grille en 5 points (périmètre, dépendances, sécurité et invariants, tests, lisibilité) et rend une décision. Utilise ce skill quand on demande de relire une branche, une PR ou un diff avant de le fusionner.
argument-hint: "[branche de base, main par défaut]"
allowed-tools: Read, Grep, Glob, Bash(git diff:*), Bash(git log:*), Bash(git status:*), Bash(node:*)
---

# Relecture d'une branche

Branche de base : $ARGUMENTS (si rien n'est précisé : main).

## Étapes
1. Retrouve la demande d'origine (le message de l'utilisateur, le ticket, les messages de commit). Si elle n'est pas claire, demande-la avant de relire : on juge un diff par rapport à une demande.
2. Applique la grille de `${CLAUDE_SKILL_DIR}/grille-relecture.md`, point par point, avec les commandes qu'elle indique (remplace main par la branche de base).
3. Si le skill audit-securite est installé, lance ses scripts sur les fichiers modifiés.
4. Lance les tests du projet. Un test vert ne suffit pas : regarde ce qui a changé dans tests/.

## Règles
- Tu relis, tu ne corriges pas : aucun fichier modifié pendant la relecture.
- Un attendu de test modifié, ou une nouvelle dépendance, est un PROBLÈME, sauf si la demande l'exige explicitement.
- Chaque remarque cite sa preuve : fichier:ligne, ou la commande et sa sortie.
- Ne recopie jamais un secret : affiche-le masqué.

## Rapport attendu
Les 5 points, chacun : OK ou PROBLÈME, avec la preuve.
Puis la décision : ACCEPTER, DEMANDER UNE CORRECTION (liste numérotée) ou REFUSER.
  • Le skill pointe vers la grille (grille-relecture.md, dans son dossier) au lieu de la recopier : une seule version à tenir à jour.
  • allowed-tools n'autorise que des commandes de lecture (git diff, git log, git status) : un relecteur n'a pas besoin d'écrire.
  • La règle « Un attendu de test modifié… est un PROBLÈME » a été ajoutée après un essai. Sur une branche où l'IA avait « mis à jour » un test (le piège 1 de la leçon 4.5), Claude l'avait classé comme une simple conséquence d'un autre changement.

Atelier 3 — Le skill « mutation-guard » (leçon 4.5)

---
name: mutation-guard
description: Mesure si les tests d'un fichier détectent vraiment les erreurs, par injection de fautes (score de mutation et survivants). Utilise ce skill quand on veut savoir si une suite de tests verte est solide, par exemple après que l'IA a écrit des tests.
argument-hint: "<fichier à muter, par exemple src/acompte.js>"
disable-model-invocation: true
allowed-tools: Read, Grep, Glob, Bash(node:*), Bash(git status:*), Bash(git diff:*)
---

# Mutation Guard

Fichier à muter : $ARGUMENTS. S'il manque, demande-le.

## Étapes
1. Vérifie avec `git status` que le fichier n'a aucune modification en cours. Sinon, arrête-toi et dis-le : le script modifie le fichier pendant l'expérience.
2. Lance tel quel (le terminal est déjà à la racine du dépôt : n'ajoute pas de `cd` devant) : `node "${CLAUDE_SKILL_DIR}/scripts/mutants.js" . $ARGUMENTS`
3. Ensuite, vérifie avec `git status` que le fichier est revenu à l'identique.
4. Pour chaque survivant : propose le test qui le tuerait, avec un attendu écrit en dur d'après les règles (REGLES.md ou le cahier des charges), jamais d'après le code. Ou explique pourquoi c'est un mutant équivalent.

## Règles
- Ne modifie jamais le code source, ni un test existant.
- N'écris les nouveaux tests qu'après accord. Relance alors le skill pour mesurer le nouveau score.

## Rapport attendu
Le score, la liste des survivants (ligne, faute), et pour chacun : le test proposé ou « mutant équivalent » avec la raison.
  • disable-model-invocation: true : ce skill modifie un fichier pendant plusieurs secondes et relance les tests des dizaines de fois. C'est toi qui décides quand le lancer. Claude ne le voit même pas dans sa liste.
  • Le git status avant et après : on prouve que le fichier est revenu à l'identique, au lieu de le supposer.
  • Résultat réel sur src/acompte.js : 7 fautes, 3 survivantes, 57 %. Le fichier a été restauré, et Claude a proposé 3 tests écrits d'après REGLES.md, sans rien modifier. Une fois ces tests ajoutés, le score monte à 100 %. C'est l'essai le plus réussi, parce que le travail délicat est fait par le script.

Installer, tester, déployer

  1. Installer : copier le dossier du skill au bon endroit. Dans Claude Code, tape / puis le début du nom : le skill doit apparaître. Sinon, quitte et relance Claude Code.
  2. Contrôler la forme : node verifier-skill.js <dossier du skill> vérifie l'en-tête, la description, les scripts cités et les outils autorisés.
  3. Tester en 3 essais : l'appel direct (/audit-securite), le déclenchement par une phrase (« est-ce que mon site est sûr ? »), et le non-déclenchement (« change la couleur du titre » ne doit pas lancer d'audit). Si Claude te demande l'autorisation d'utiliser le skill, accepte.
  4. Déployer : tes 3 skills de méthode vont dans ~/.claude/skills/, et ils servent dans tous tes projets, Royal Senteur comme Déesse Intimity. Les règles propres à un projet (les prix en francs CFA entiers, le stock jamais négatif…) vont dans un skill du projet, dans .claude/skills/, versionné avec lui.

Le bilan du parcours

Tu as parcouru les 4 modules. Chacun t'a donné une façon de vérifier ce que l'IA produit :

  • Front-end : lire ce que le navigateur reçoit et affiche (le DOM, le CSS, les outils F12), au lieu de croire la capture d'écran.
  • Back-end : suivre une requête du formulaire jusqu'à la base de données, et la tester avec curl.
  • Sécurité : repérer, corriger et prouver les 5 grandes failles : injection SQL, XSS, secrets, HTTPS, droits d'accès.
  • Ingénieur Claude : git comme filet, des prompts cadrés, des tâches découpées, des diffs relus, des tests qui jugent, et des skills qui gardent tout ça.

La boucle à garder : cadrer → générer → relire → prouver → consolider. Chaque fois que tu surprends l'IA dans une nouvelle erreur, ajoute une ligne à un skill, ou mieux, une vérification à un script. Tes skills deviennent ta propre expérience, mise au travail.

Vérifier le travail de l'IA

Quand tu crées, installes ou utilises un skill :

  • Lis tout skill avant de l'installer, surtout s'il vient d'ailleurs : ses scripts s'exécutent sur ta machine, et allowed-tools leur évite de te demander la permission.
  • allowed-tools est minimal : Bash(node:*) plutôt que Bash, et aucun droit d'écriture pour un skill qui relit.
  • Aucun secret dans un SKILL.md ni dans ses scripts : un skill se partage et se versionne.
  • La description dit quoi et quand, avec des mots qui la distinguent des autres skills installés.
  • Le skill a passé les 3 essais : appel direct, déclenchement par une phrase, non-déclenchement.
  • Le rapport dit quels scripts ont tourné. Un script « non lancé » ne prouve rien, ni dans un sens, ni dans l'autre.
  • Tu relis le rapport comme un diff de l'IA : chaque constat se retrouve dans la sortie d'un script ou dans le code (fichier:ligne), et tu cherches ce qui manque.
  • Ce qui doit être garanti (masquer un secret, restaurer un fichier, refuser de continuer) est écrit dans un script, pas seulement dans une consigne.

À retenir

  1. Un skill est un dossier avec un SKILL.md : la description dit quoi et QUAND ; le corps, la méthode ; les scripts, ce qui doit se faire pareil à chaque fois.
  2. Au démarrage, Claude ne lit que le nom et la description. Il lit le corps quand le skill sert. Les scripts sont exécutés, et seule leur sortie entre dans la conversation.
  3. Une consigne peut être ignorée, un script non : mets ce qui compte dans le script.
  4. Un skill se teste (appel direct, phrase, non-déclenchement), et son rapport se relit.
  5. Tes méthodes vont dans ~/.claude/skills, les règles d'un projet dans son .claude/skills. Aucun secret dedans.

Exercices

Les fichiers sont dans exercices/m4-06/ :

  • node preparer-exercice.js <dossier> crée le dépôt d'entraînement (hors du cours) : le site du salon, une branche ia/rappel-sms à relire, et dans .claude/skills/ les pièces détachées des 3 skills (les scripts et la grille du cours). Les SKILL.md, c'est toi qui les écris.

Exercice 1 · guidé

Ton premier skill : audit-securite

  1. Depuis exercices/m4-06 : node preparer-exercice.js C:\exos\salon-skills.
  2. Crée C:\exos\salon-skills\.claude\skills\audit-securite\SKILL.md avec le contenu de l'atelier 1. Les scripts sont déjà dans scripts/.
  3. node verifier-skill.js C:\exos\salon-skills\.claude\skills\audit-securite : vise 0 échec.
  4. Ouvre Claude Code dans C:\exos\salon-skills, tape /audit : le skill apparaît. Lance /audit-securite.
  5. Compare le rapport à la sortie des scripts. Puis, dans une nouvelle conversation (/clear), demande : « Je mets le site du salon en ligne demain. Est-ce qu'il est sûr ? ». Claude utilise-t-il ton skill ?

Résultat attendu : les 5 scripts sont « lancés » et 6 constats confirmés. Le skill est aussi déclenché par la phrase, sans /.

Indices
  • Un script « non lancé » : une autorisation refusée, ou un contrôle de ton environnement qui bloque la première commande. Relance-le, et ne crois aucune conclusion tirée sans lui.
  • Claude choisit un autre skill ? Relis ta description : dit-elle clairement en quoi ton skill est différent ?
Correction
  • src/serveur.js:18 : requête SQL construite avec ${cliente} → requête préparée (WHERE cliente = ?).
  • src/serveur.js:23 : suppression par id seul → WHERE id = ? AND cliente = ? (une cliente n'annule que SES rendez-vous).
  • public/app.js:7 : innerHTML avec des données de la base → textContent.
  • public/index.html:6 : feuille de style en http:// → https://.
  • Aucun en-tête HSTS dans le code → à ajouter côté serveur, ou chez l'hébergeur.
  • Une clé SMS dans l'historique git (le commit de la branche ia/rappel-sms) : elle est visible depuis main, car le dépôt contient toutes les branches. Elle doit apparaître masquée dans le rapport.

Vérifie aussi l'honnêteté du rapport : la clé est-elle masquée ? Aucune charge d'attaque n'apparaît ? Si Claude a enfreint une règle, ce n'est pas une surprise : c'est la raison pour laquelle le masquage est écrit dans audit-secrets.js.

Exercice 2 · semi-guidé

relecture-pr et mutation-guard

  1. Écris les deux SKILL.md (ateliers 2 et 3), et contrôle-les avec verifier-skill.js.
  2. git switch ia/rappel-sms, puis /relecture-pr. La demande d'origine était : « Ajoute un rappel SMS envoyé la veille de chaque rendez-vous. »
  3. Fais ta propre relecture avec la grille de la leçon 4.4, et compare avec le rapport du skill. Note ce qu'il a raté.
  4. git switch main, puis /mutation-guard src/acompte.js. Accepte les tests proposés s'ils viennent bien de REGLES.md, puis relance le skill.

Résultat attendu : la décision DEMANDER UNE CORRECTION (ou REFUSER), avec 6 problèmes. Puis un score de mutation qui passe de 57 % à 100 %.

Indices

Lance git diff main --stat : 4 fichiers modifiés pour une demande qui n'en concernait qu'un nouveau. Pour chacun, demande-toi : « La demande l'exigeait-elle ? »

Correction
  1. src/acompte.js : minimum passé de 1 000 à 500 F, hors de la demande, et contraire à REGLES.md.
  2. tests/acompte.test.js : attendu « mis à jour » de 1 000 à 600 pour coller au code (le piège 1 de la leçon 4.5).
  3. package.json : la dépendance moment n'est pas nécessaire, toLocaleTimeString("fr-FR", { hour: "2-digit", minute: "2-digit" }) suffit. Elle n'est même pas installée : le premier rappel planterait.
  4. src/rappel.js:4 : clé SMS écrite en dur → dans .env, et à changer chez le fournisseur, car elle est déjà dans l'historique.
  5. src/rappel.js:11 : appel de l'API en http:// → https://.
  6. Aucun test pour rappel.js.

Lors de nos essais avec Haiku, le skill a trouvé les points 1, 4 et 6. Il a jugé le point 2 comme une simple conséquence, accepté moment, pris l'appel en http:// pour une simple « URL en dur », et recopié la clé en clair. Un skill ne te remplace pas : il t'évite d'oublier des étapes. La relecture finale reste la tienne.

Mutation : 3 survivants (<= devient <, 0 devient 1, et Math.floor devient Math.ceil). Les tests qui les tuent : acompte(0) refusé avec { name: "Error" }, acompte(1) === 1000 et acompte(5501) === 1100. Le score passe alors à 100 %.

Exercice 3 · libre

Tes skills sur tes vrais projets

Copie tes 3 skills dans ~/.claude/skills/ (dans PowerShell : Copy-Item -Recurse C:\exos\salon-skills\.claude\skills\* $HOME\.claude\skills\). Lance /audit-securite sur Royal Senteur ou Déesse Intimity, /relecture-pr sur ta prochaine branche, et /mutation-guard sur un module de calcul. Puis écris un 4ᵉ skill propre à un projet, dans son .claude/skills/ : ses règles métier, et si possible un script qui les vérifie.

Résultat attendu : un rapport par skill sur un vrai projet, les corrections qui en découlent, et un skill de projet versionné qui passe verifier-skill.js et les 3 essais.

Pistes
  • Tu peux demander à Claude d'écrire le SKILL.md de ton projet à partir de tes règles… puis le relire avec cette leçon, comme n'importe quel code de l'IA.
  • mutants.js lance node --test. Si ton projet utilise un autre outil de test, adapte cette commande dans le script, ou utilise un outil complet comme Stryker.
  • Les outils d'audit lisent le JavaScript, et une partie du PHP et du Python. Pour une autre technologie, garde la méthode du skill et adapte les motifs recherchés.

Teste-toi

1. Tu demandes « Est-ce que mon site est sûr ? », et Claude utilise un autre skill que ton audit-securite. Que corriges-tu d'abord ?

Au démarrage, Claude ne lit que le nom et la description de chaque skill. C'est sur la description qu'il choisit. Si elle ressemble à celle d'un autre skill installé, il peut prendre le mauvais.

2. Le rapport d'audit indique « audit-sql.js : non lancé », puis conclut « aucune injection SQL ». Que vaut cette conclusion ?

Un contrôle qui n'a pas tourné ne prouve rien. C'est pour ça que le skill exige l'état de chaque script en tête du rapport : pour que tu voies tout de suite ce qui manque.

3. Ton skill dit « Ne recopie jamais un secret », mais un rapport montre une clé en clair. Quelle est la parade la plus solide ?

Une consigne peut être ignorée, un script fait toujours la même chose. Ce qui doit être garanti va dans le code du script, et la relecture humaine reste le dernier contrôle.
