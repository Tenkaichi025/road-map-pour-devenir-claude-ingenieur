Leçon 4.5

Les tests verts qui ne prouvent rien

L'idée

« Tous les tests passent » : c'est la phrase la plus rassurante… et la plus trompeuse de l'IA. Un test vert dit seulement « ce que j'ai vérifié est vrai ». Il ne dit rien de ce qu'il n'a pas vérifié. Une suite 100 % verte peut donc cacher une application cassée : elle teste les mauvaises choses, ou les teste de travers.

Un bon test a une seule qualité qui compte : il passe au rouge quand le code est faux. D'où la parade de l'ingénieur, l'injection de fautes (on dit aussi mutation testing). On abîme volontairement le code (un > devient >=, un 10 devient 11), puis on relance les tests. S'ils restent verts, ils ne protègent pas cette partie du code.

Exemple concret

Le module de devis d'une boutique. Les règles sont écrites dans REGLES.md : 10 % de remise à partir de 5 commandes, arrondie au franc inférieur ; livraison de 2 000 F, offerte à partir de 50 000 F inclus ; quantités entières d'au moins 1. La suite de tests : 7 tests, tous verts. Le code contient pourtant 4 bugs. Voici les 4 pièges qui les cachent.

Piège 1 — L'assertion altérée

test("Client fidèle : 10 % de remise", () => {
  assert.equal(remiseFidelite(24000, 4), 2400); // mis à jour pour correspondre au code
});

La règle dit « à partir de 5 commandes ». Le code donne la remise dès 4 commandes. Le test échouait, alors on a « mis à jour » le test pour qu'il colle au code. Désormais, le test protège le bug. C'est exactement ce que fait une IA à qui l'on demande « fais passer les tests » (leçon 4.1).

Piège 2 — L'erreur d'exécution prise pour une validation

test("Un devis invalide est refusé", () => {
  assert.throws(() => calculerDevis(undefined));
});

Le test passe… parce que undefined.reduce plante (une TypeError), pas parce que le code valide quoi que ce soit. Une quantité de -2 est d'ailleurs acceptée sans broncher. C'est le piège trouvé en construisant la leçon 4.3 : des tests de « refus » qui passaient sur un fichier vide. La parade : exiger une vraie erreur de validation, avec assert.throws(fn, { name: "Error" }), et tester avec des données presque valides (une quantité de -2), pas avec undefined.

Piège 3 — Le test tautologique, ou qui teste son propre mock

test("La remise vaut 10 % du montant", () => {
  const montant = 31995;
  assert.equal(remiseFidelite(montant, 6), Math.round(montant * 0.1));   // recopie le calcul du code
});

test("Livraison offerte pour les grosses commandes", (t) => {
  t.mock.method(devis, "fraisLivraison", () => 0);    // remplace la vraie fonction par « renvoie 0 »
  assert.equal(devis.fraisLivraison(80000), 0);        // … et vérifie que le faux renvoie 0
});

Le premier recalcule l'attendu avec la même formule que le code, y compris le mauvais arrondi : il ne peut jamais échouer. Le second remplace la fonction par un faux (un mock), puis teste le faux : le vrai code n'est jamais exécuté. Un attendu s'écrit en dur, calculé à la main d'après la règle : 10 % de 31 995 F, arrondis vers le bas, font 3 199 F.

Piège 4 — La couverture aveugle

Tous les tests passent par le « cas heureux » : 24 000 F, 30 000 F, 80 000 F. Aucun ne touche les limites : 50 000 F pile, 4 et 5 commandes, une quantité de 1, un montant qui donne des centimes. Or c'est là que vivent les bugs. Le code écrit montant > 50000 au lieu de >= : le client à 50 000 F pile paie la livraison, et aucun test ne le voit.

La parade : injecter des fautes

node mutants.js C:\exos\devis-tests src/devis.js

16 fautes injectées dans src/devis.js : 10 détectée(s) par les tests, 6 survivante(s).
SURVIVANT  ligne 11 : Math.round devient Math.ceil
SURVIVANT  ligne 16 : « > » devient « >= »
SURVIVANT  ligne 22 : « - » devient « + »
…
Score de mutation : 63 %.

Chaque survivant indique un test qui manque : on peut changer l'arrondi, déplacer la limite des 50 000 F, ou ajouter la remise au lieu de la soustraire dans le devis complet, et la suite reste verte. Ensuite, on écrit des tests à partir des règles (pas à partir du code) : 4 commandes donnent 0, 5 commandes 2 400, 2 995 F donnent 299, 50 000 F pile donnent 0, une quantité de -2 est refusée. Ils passent au rouge 5 fois : les 4 bugs apparaissent. On corrige le code, sans toucher aux nouveaux tests, et tout repasse au vert.

Relancé ensuite, l'outil montre encore des survivants. Deux sortes : les vrais trous (aucun test ne combine remise et devis complet, rien ne vérifie qu'une quantité de 1 est acceptée), à combler par un test. Et les mutants équivalents : des fautes qui ne changent rien au comportement (une valeur par défaut de 0 ou de 1 commande, quand la remise commence à 5). Ceux-là, on les note, et on passe.

Vérifier le travail de l'IA

Quand l'IA écrit ou modifie des tests :

  • Aucun test existant n'a vu son attendu changer sans que la règle ait changé. Un commentaire « mis à jour pour correspondre au code » est une alerte rouge.
  • Les tests de refus exigent une vraie erreur de validation ({ name: "Error" } ou un message précis), avec des données presque valides, pas undefined.
  • Les attendus sont écrits en dur, calculés à la main d'après la règle. Jamais recalculés avec la formule du code.
  • Aucun mock ne remplace la fonction même qu'on prétend tester. Un mock sert à isoler une dépendance (le réseau, la date), pas le code testé.
  • Les limites sont testées : pile sur le seuil, juste en dessous, juste au-dessus, zéro, une valeur négative, un montant qui donne des centimes.
  • Les tests sont écrits à partir des règles (le cahier des charges), pas en lisant le code : sinon, ils recopient ses bugs.
  • Lance l'injection de fautes. Chaque survivant est soit un test à ajouter, soit un mutant équivalent que tu sais justifier.

À retenir

  1. Un test vert prouve seulement ce qu'il vérifie. Un bon test passe au rouge quand le code est faux.
  2. Les 4 pièges : l'assertion altérée, la TypeError prise pour une validation, la tautologie ou le mock, la couverture aveugle.
  3. Les attendus s'écrivent en dur, à partir des règles. Les limites se testent toujours.
  4. Injecter des fautes révèle les tests inutiles : chaque survivant est un test qui manque.
  5. Ne laisse jamais l'IA modifier un test pour faire passer son code : c'est le test qui juge, pas l'inverse.

Exercice 3 · libre

Le score de mutation de ton projet

Choisis un module de calcul dans un de tes projets (un panier, des frais, des stocks…) qui a des tests. Lance mutants.js dessus. Pour chaque survivant : écris le test qui manque, ou explique pourquoi c'est un mutant équivalent. Repère aussi les 4 pièges dans la suite existante.

Résultat attendu : le score avant et après, les tests ajoutés, et la liste des pièges trouvés dans tes tests actuels.

Pistes
  • Pas de tests du tout ? Le score sera de 0 % : commence par une règle et ses limites.
  • Pour un vrai projet, il existe des outils complets d'injection de fautes (Stryker pour JavaScript). mutants.js suffit pour comprendre le principe et repérer les pires trous.

Teste-toi

1. Un test contient assert.equal(remiseFidelite(24000, 4), 2400); // mis à jour pour correspondre au code, alors que la règle dit « à partir de 5 commandes ». Quel est le problème ?

L'attendu d'un test vient de la règle, jamais du code. Ici, on a changé l'attendu pour faire taire un test qui avait raison. C'est la pire forme de test vert.

2. Une faute injectée (« > » devient « >= » dans la livraison) laisse tous les tests verts. Que faut-il en conclure ?

Un survivant signifie que cette partie du code pourrait changer sans qu'aucun test ne le remarque. Le test qui manque est celui qui se place exactement sur la limite.

3. Tu demandes à Claude d'écrire les tests d'un module. Quelle consigne est la plus importante ?

Des tests écrits en lisant le code recopient ses bugs. « Fais passer les tests » pousse à modifier les tests. Les règles sont la seule référence indépendante du code.
