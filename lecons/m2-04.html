Leçon 2.4

Authentifier les utilisateurs

L'idée

S'authentifier, c'est prouver qui on est : l'e-mail et le mot de passe. Le serveur ne garde jamais le mot de passe lui-même. Il garde une empreinte (un hash) : un calcul à sens unique, impossible à remonter. À la connexion, il refait le calcul et compare. Si la base fuit un jour, les mots de passe ne sont pas lisibles.

HTTP n'a aucune mémoire : chaque requête arrive seule, sans savoir qui l'envoie. Après une connexion réussie, le serveur remet donc un ticket au navigateur, rangé dans un cookie. Le navigateur le renvoie tout seul à chaque requête suivante. C'est la session.

Il existe une autre approche, le JWT : un jeton signé qui contient lui-même les informations (qui tu es, jusqu'à quand). C'est pratique quand plusieurs serveurs doivent le lire. Mais on ne peut pas facilement l'annuler avant son expiration, et l'IA le range souvent dans le localStorage, où n'importe quel script de la page peut le lire. Pour un site classique, une session dans un cookie protégé est plus simple et plus sûre.

Enfin, le contrôle d'accès : chaque route privée doit vérifier la session avant de répondre. Il suffit d'une route oubliée pour tout exposer.

Exemple concret

Un espace membre avec une page de connexion et des notes privées. Tout est en Node.js natif : node:crypto pour le hachage, node:sqlite pour les comptes. Rien à installer.

Hacher le mot de passe

const crypto = require("node:crypto");

function hacher(motDePasse) {
  const sel = crypto.randomBytes(16);                        // un sel différent pour chaque compte
  const empreinte = crypto.scryptSync(motDePasse, sel, 64);  // lent exprès
  return `${sel.toString("hex")}:${empreinte.toString("hex")}`;
}

function verifierMotDePasse(motDePasse, stocke) {
  const [selHex, empreinteHex] = stocke.split(":");
  const attendue = Buffer.from(empreinteHex, "hex");
  const calculee = crypto.scryptSync(motDePasse, Buffer.from(selHex, "hex"), 64);
  return crypto.timingSafeEqual(attendue, calculee);         // comparaison en temps constant
}
  • Le sel est une valeur aléatoire ajoutée au mot de passe avant le calcul. Deux personnes avec le même mot de passe obtiennent donc deux empreintes différentes, et les listes d'empreintes précalculées ne servent à rien.
  • scrypt est lent exprès (environ 70 ms) : invisible pour un visiteur, mais un attaquant qui veut tester des millions de mots de passe est fortement ralenti. md5 ou sha256 seuls sont beaucoup trop rapides pour cet usage.

Se connecter : vérifier, puis donner un ticket

const utilisateur = sql.utilisateurParEmail.get(email);
const correct = utilisateur && verifierMotDePasse(motDePasse, utilisateur.hash);
if (!correct) return repondre(res, 401, { erreur: "E-mail ou mot de passe incorrect." });

const idSession = crypto.randomBytes(32).toString("base64url");   // impossible à deviner
sessions.set(idSession, { utilisateurId: utilisateur.id, expire: Date.now() + 2 * 3600 * 1000 });
res.setHeader("Set-Cookie", `session=${idSession}; HttpOnly; SameSite=Lax; Path=/; Max-Age=7200`);

Le message d'erreur est le même, que l'e-mail existe ou non. Sinon, un inconnu pourrait tester une liste d'e-mails pour savoir lesquels ont un compte.

Les options du cookie

OptionCe qu'elle protège
HttpOnlyLe JavaScript de la page ne peut pas lire le cookie. Un script injecté (faille XSS, leçon 3.2) ne peut donc pas voler la session.
SameSite=LaxLe cookie n'est pas envoyé quand un autre site soumet un formulaire vers le tien. C'est la protection contre la faille CSRF.
SecureLe cookie ne voyage qu'en HTTPS. Obligatoire en ligne (absent ici, car localhost est en HTTP).
Max-AgeLa session expire : un cookie volé ne sert pas éternellement.

La faille CSRF, c'est quand un site piégé fait envoyer une requête à ton site par le navigateur du visiteur, avec son cookie, et donc en son nom. Par exemple : « supprimer mon compte ».

La garde, en tête de chaque route privée

function exigerConnexion(req, res) {
  const id = lireCookies(req).session;
  const session = id && sessions.get(id);
  if (!session || session.expire < Date.now()) {
    repondre(res, 401, { erreur: "Connecte-toi d'abord." });
    return null;
  }
  return session.utilisateurId;
}

// Chaque route privée commence ainsi :
const moi = exigerConnexion(req, res);
if (!moi) return;
return repondre(res, 200, sql.notesDe.all(moi));     // seulement SES notes

Vérifier le travail de l'IA

Quand l'IA code une inscription, une connexion ou une route privée :

  • Aucun mot de passe en clair : la base contient une empreinte faite avec scrypt, bcrypt ou argon2, avec un sel. Jamais md5 ou sha256 seuls. Test : regarde la table.
  • Le mot de passe n'est jamais renvoyé dans une réponse, ni écrit dans les journaux (console.log du corps reçu).
  • Même message d'erreur que l'e-mail existe ou non.
  • Le cookie de session contient une valeur aléatoire et longue, jamais l'e-mail ou l'id de l'utilisateur. Il a HttpOnly et SameSite=Lax, plus Secure en ligne. Test : F12 → Application → Cookies, puis document.cookie dans la Console ne doit pas l'afficher.
  • Aucun jeton de connexion dans le localStorage : tout script de la page peut le lire.
  • Chaque route privée appelle la garde. Test : appelle chaque route sans cookie, tu dois obtenir 401. Méfie-toi des routes « de débogage » ou « admin » ajoutées en passant.
  • La déconnexion supprime la session côté serveur. Test : garde l'ancien cookie, et rappelle une route privée après la déconnexion : 401 attendu.
  • Les sessions expirent, et un mot de passe trop court est refusé à l'inscription.

À retenir

  1. On ne stocke jamais un mot de passe : on stocke son empreinte, avec un sel et un algorithme lent.
  2. Après la connexion, le serveur remet un ticket aléatoire dans un cookie. Le navigateur le renvoie tout seul.
  3. Cookie de session : HttpOnly, SameSite=Lax, Secure en ligne, et une durée de vie.
  4. Session dans un cookie pour un site classique. Jamais de jeton dans le localStorage.
  5. Chaque route privée commence par la garde. Teste-les toutes sans cookie : 401 partout.

Exercice 1 · guidé

Suivre une session de bout en bout

  1. Dans exercices/m2-04/espace-membre, lance node serveur.js. Ouvre http://localhost:3006 et connecte-toi avec le compte d'Awa : ses notes s'affichent.
  2. F12 → onglet Application → Cookies → http://localhost:3006. Regarde la valeur du cookie session et la colonne HttpOnly.
  3. Dans l'onglet Console, tape document.cookie.
  4. Déconnecte-toi. Essaie un mauvais mot de passe, puis un e-mail qui n'existe pas. Compare les deux messages.
  5. Dans un deuxième terminal, depuis exercices/m2-04/requetes :
curl.exe -si http://localhost:3006/api/notes
curl.exe -si -c cookies-awa.txt -X POST http://localhost:3006/api/connexion -H "Content-Type: application/json" --data "@connexion-awa.json"
curl.exe -s -b cookies-awa.txt http://localhost:3006/api/notes
curl.exe -si -b "session=awa@exemple.ci" http://localhost:3006/api/notes
curl.exe -si -b cookies-awa.txt -X POST http://localhost:3006/api/deconnexion
curl.exe -si -b cookies-awa.txt http://localhost:3006/api/notes
  1. Enfin, dans exercices/m2-04/espace-membre : node sql.js "SELECT email, hash FROM utilisateurs".

Résultat attendu : le cookie est long, aléatoire et marqué HttpOnly, et document.cookie ne le montre pas. Les deux erreurs de connexion affichent le même message. Côté curl : 401, 200, les notes, 401 avec le faux cookie, 204, puis 401. La base ne contient que des empreintes.

Indices

Ouvre cookies-awa.txt dans ton éditeur : c'est le cookie que curl a reçu et qu'il renvoie avec -b.

Correction
  • document.cookie renvoie "" : grâce à HttpOnly, aucun script de la page ne peut lire la session. Le navigateur l'envoie pourtant à chaque requête.
  • Mauvais mot de passe ou e-mail inconnu : « E-mail ou mot de passe incorrect. » dans les deux cas.
  • Sans cookie : 401. Après la connexion : 200 et un en-tête Set-Cookie: session=…; HttpOnly; SameSite=Lax.
  • Le faux cookie session=awa@exemple.ci donne 401 : il ne correspond à aucune session. Impossible de se faire passer pour Awa en connaissant son e-mail.
  • Après la déconnexion (204), l'ancien cookie ne marche plus (401) : la session a été supprimée sur le serveur.
  • La colonne hash contient sel:empreinte en hexadécimal. Aucune trace de mangue-papaye-2026.

Indices

Être connecté ne suffit pas : il faut aussi que la note appartienne à la personne connectée. Regarde la requête SQL écrite par Claude : vérifie-t-elle à qui appartient la note ?

Correction

La bonne version vérifie les deux choses dans la même requête SQL :

const moi = exigerConnexion(req, res);
if (!moi) return;
const { changes } = db
  .prepare("DELETE FROM notes WHERE id = ? AND utilisateur_id = ?")
  .run(Number(trouve[1]), moi);
return changes === 0 ? repondre(res, 404, { erreur: "Note introuvable." }) : repondre(res, 204);

L'erreur classique : DELETE FROM notes WHERE id = ? seul. Kofi, connecté, peut alors supprimer les notes de tout le monde, juste en changeant le numéro dans l'adresse. Il est authentifié, mais il n'est pas autorisé. On creuse cette différence à la leçon 3.5.

Pourquoi 404 plutôt que 403 ? Pour ne même pas révéler à Kofi que la note n°1 existe.

Preuve : curl.exe -s -b "session=awa@exemple.ci" http://localhost:3007/api/notes renvoie les notes d'Awa. N'importe qui connaissant son e-mail entre chez elle. Et un script injecté pourrait lire le cookie.

Teste-toi

1. La base de données de ton site fuite. Qu'est-ce qui protège les mots de passe de tes clients ?

HTTPS protège ce qui circule sur le réseau, et HttpOnly protège le cookie dans le navigateur. Mais si la base elle-même fuit, seul le hachage protège les mots de passe : l'attaquant n'obtient que des empreintes, très longues à attaquer une par une.

2. Que garantit l'option HttpOnly d'un cookie ?

HttpOnly cache le cookie aux scripts : même un script malveillant injecté dans la page ne peut pas le voler. C'est Secure qui le limite au HTTPS, et Max-Age qui règle sa durée.

3. L'IA a ajouté une route /api/admin/export « pour déboguer ». Que vérifies-tu en premier ?

Les routes ajoutées « en passant » sont les plus souvent oubliées par le contrôle d'accès. Appelle-la sans cookie. Et si tu n'en as pas besoin en production, demande plutôt à l'IA de la supprimer.
