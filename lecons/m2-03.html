Leçon 2.3

Conserver les données avec SQLite

L'idée

En 2.1, les réservations disparaissaient à chaque redémarrage du serveur. Elles vivaient dans la mémoire du programme, et cette mémoire est effacée dès qu'il s'arrête. Pour garder des données, il faut les écrire dans un fichier. Une base de données, c'est un fichier organisé pour ça.

Avec SQLite, toute la base tient dans un seul fichier, par exemple blog.db. À l'intérieur, des tables : des tableaux avec des colonnes fixes et une ligne par élément. On leur parle dans un langage dédié, le SQL, avec quatre verbes : INSERT (créer), SELECT (lire), UPDATE (modifier), DELETE (supprimer).

Le grand danger : coller une valeur venue d'un visiteur directement dans le texte d'une requête SQL. Le visiteur peut alors écrire du SQL à ta place. C'est l'injection SQL. La protection tient en une règle : les requêtes préparées. Le SQL contient des ?, et les valeurs voyagent à part.

Exemple concret

Un blog de bonnes adresses : des articles, et des commentaires sous chaque article. Certains articles sont des brouillons qui ne doivent jamais être visibles. Le serveur utilise node:sqlite, fourni avec Node (version 22.5 ou plus) : rien à installer.

Ouvrir la base et créer les tables

const { DatabaseSync } = require("node:sqlite");
const db = new DatabaseSync("blog.db");     // le fichier est créé s'il n'existe pas

db.exec(`
  CREATE TABLE IF NOT EXISTS articles (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    titre   TEXT    NOT NULL,
    contenu TEXT    NOT NULL,
    publie  INTEGER NOT NULL DEFAULT 0          -- 0 = brouillon, 1 = publié
  );
  CREATE TABLE IF NOT EXISTS commentaires (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    article_id INTEGER NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
    auteur     TEXT    NOT NULL,
    texte      TEXT    NOT NULL
  );
`);
  • PRIMARY KEY AUTOINCREMENT : la base numérote elle-même chaque ligne.
  • NOT NULL : ce champ est obligatoire. La base refuse une ligne sans lui.
  • REFERENCES articles(id) : c'est une clé étrangère. Chaque commentaire pointe vers un article qui existe vraiment. ON DELETE CASCADE : quand on supprime un article, ses commentaires partent avec lui.

Les quatre verbes, face aux routes de l'API

SQLRôleRoute REST
INSERT INTO articles (titre, …) VALUES (?, …)CréerPOST
SELECT id, titre FROM articles WHERE publie = 1LireGET
UPDATE articles SET titre = ? WHERE id = ?ModifierPUT
DELETE FROM articles WHERE id = ?SupprimerDELETE

Attention : un UPDATE ou un DELETE sans WHERE touche toutes les lignes de la table.

Des requêtes préparées

Dans le serveur, chaque requête est préparée une fois, avec des ? à la place des valeurs :

const sql = {
  articlePublie: db.prepare("SELECT id, titre, contenu FROM articles WHERE id = ? AND publie = 1"),
  supprimerArticle: db.prepare("DELETE FROM articles WHERE id = ?"),
};

const article = sql.articlePublie.get(id);    // une ligne, ou undefined si elle n'existe pas
if (!article) return repondre(res, 404, { erreur: "Article introuvable." });

const { changes } = sql.supprimerArticle.run(id);   // changes = nombre de lignes supprimées
if (changes === 0) return repondre(res, 404, { erreur: "Article introuvable." });

L'injection SQL, en vrai

Une recherche dans les titres, écrite comme l'IA le fait trop souvent :

// DANGER : la valeur q est collée dans le texte SQL
db.prepare(`SELECT id, titre FROM articles WHERE publie = 1 AND titre LIKE '%${q}%'`).all();

Un visiteur cherche %' OR 1=1 --. Le serveur exécute alors :

SELECT id, titre FROM articles WHERE publie = 1 AND titre LIKE '%%' OR 1=1 --%'

L'apostrophe a fermé le texte, OR 1=1 est vrai pour toutes les lignes, et -- transforme la fin en commentaire. Résultat : les brouillons confidentiels apparaissent. Et un visiteur honnête qui cherche « l'attiéké » fait planter le serveur, à cause de son apostrophe. La version correcte : 

// La valeur voyage à part : quoi qu'elle contienne, elle reste une valeur
db.prepare("SELECT id, titre FROM articles WHERE publie = 1 AND titre LIKE ?").all(`%${q}%`);

Remarque : prepare ne protège rien si le SQL est déjà collé avant. Ce qui protège, c'est le ?. Le module 3 (leçon 3.1) va plus loin sur les attaques.

Ouvrir une fois, fermer à la fin

const db = new DatabaseSync("blog.db");     // au démarrage, une seule fois

process.on("SIGINT", () => {                 // Ctrl + C
  db.close();                                // on ferme proprement avant de quitter
  process.exit(0);
});

Ouvrir la base à chaque requête, c'est au mieux du travail inutile (ouvrir le fichier, relire sa structure) répété à chaque visiteur. Au pire, si on ne la ferme jamais, des connexions restent ouvertes et s'accumulent sur un serveur très sollicité. La règle est simple : une connexion, ouverte au démarrage, fermée à l'arrêt.

Vérifier le travail de l'IA

Quand l'IA écrit du code qui parle à une base de données :

  • Aucune valeur venue de l'extérieur (adresse, formulaire, JSON) n'est collée dans une chaîne SQL. Cherche ${ et + à l'intérieur des requêtes : tout doit passer par des ?.
  • Test : une apostrophe dans un texte (« l'attiéké ») ne fait rien planter, et %' OR 1=1 -- ne renvoie rien de plus.
  • La base est ouverte une fois au démarrage, et fermée à l'arrêt. Jamais un new DatabaseSync(…) dans une route, appelé à chaque requête.
  • Les contraintes restent actives. Si l'IA écrit enableForeignKeyConstraints: false ou PRAGMA foreign_keys = OFF pour « régler » une erreur, refuse : la base signalait un vrai problème.
  • Les colonnes obligatoires ont NOT NULL, et les liens ont REFERENCES.
  • Une lecture par id gère l'absence (get() renvoie undefined → 404). Un DELETE vérifie changes. Et aucun UPDATE ou DELETE n'existe sans WHERE.
  • Les données privées (brouillons) sont filtrées dans la requête SQL, pas seulement par la page.
  • Le fichier .db n'est pas commité dans git : il contient de vraies données.

À retenir

  1. En mémoire, tout disparaît au redémarrage. Dans une base, les données vivent dans un fichier.
  2. Une base contient des tables, liées par des clés : article_id pointe vers articles.id.
  3. Quatre verbes : INSERT, SELECT, UPDATE, DELETE. Jamais les deux derniers sans WHERE.
  4. Jamais de valeur collée dans le SQL : une requête préparée, avec des ?.
  5. Une connexion ouverte au démarrage, fermée à l'arrêt. Et des contraintes qu'on ne désactive jamais.

Exercices

Les fichiers sont dans exercices/m2-03/. L'outil sql.js te permet d'envoyer une requête SQL à la base, sans rien installer : node sql.js "TA REQUÊTE". Le fichier blog.db est créé automatiquement au premier lancement, avec quelques données de départ.

Exercice 1 · guidé

Parler SQL à la base du blog

  1. Ouvre un terminal dans exercices/m2-03/blog, puis lis les articles :
node sql.js "SELECT id, titre, publie FROM articles"
  1. Lis les commentaires avec le titre de leur article. JOIN relie les deux tables grâce à la clé :
node sql.js "SELECT a.titre, c.auteur, c.texte FROM commentaires c JOIN articles a ON a.id = c.article_id"
  1. Ajoute un commentaire, modifie un titre, puis relis :
node sql.js "INSERT INTO commentaires (article_id, auteur, texte) VALUES (2, 'Yao', 'Adresse validée')"
node sql.js "UPDATE articles SET titre = 'Les maquis de Yopougon' WHERE id = 2"
  1. Essaie d'ajouter un commentaire à un article qui n'existe pas :
node sql.js "INSERT INTO commentaires (article_id, auteur, texte) VALUES (999, 'Yao', 'Test')"
  1. Lance le serveur (node serveur.js). Depuis exercices/m2-03/requetes, crée un article : curl.exe -si -X POST http://localhost:3004/api/articles -H "Content-Type: application/json" --data "@nouvel-article.json".
  2. Arrête le serveur (Ctrl + C), relance-le, puis ouvre http://localhost:3004/api/articles.
  3. Supprime l'article n°1 : curl.exe -si -X DELETE http://localhost:3004/api/articles/1. Puis cherche ses commentaires avec sql.js : SELECT * FROM commentaires WHERE article_id = 1.

Résultat attendu : les trois articles, dont un brouillon (publie = 0). La base refuse le commentaire sur l'article 999. Ton article est toujours là après le redémarrage. Les commentaires de l'article 1 ont disparu avec lui.

Indices

En SQL, le texte s'écrit entre apostrophes simples : 'Yao'. Pour mettre une apostrophe dans un texte, on la double : 'l''attiéké'.

Pour repartir des données de départ, arrête le serveur et supprime le fichier blog.db : il sera recréé au prochain lancement.

Correction
  • Le JOIN affiche 3 commentaires, chacun avec le titre de son article.
  • L'INSERT et l'UPDATE affichent « 1 ligne(s) modifiée(s) ».
  • Le commentaire sur l'article 999 donne Erreur SQL : FOREIGN KEY constraint failed. C'est la clé étrangère qui protège tes données. node:sqlite active ce contrôle par défaut.
  • Après le redémarrage, l'article « Le garba du vendredi » est toujours là : il est écrit dans blog.db. C'est la différence avec la leçon 2.1.
  • Après le DELETE (code 204), la requête ne renvoie aucun commentaire : ON DELETE CASCADE les a supprimés avec l'article.
Exercice 2 · semi-guidé

Faire ajouter une recherche par Claude, puis l'attaquer

  1. Copie le dossier blog dans un dossier de travail. Dans la copie, demande à Claude :
Dans serveur.js, ajoute une route GET /api/recherche?q=... qui
renvoie les articles publiés dont le titre contient q.
  1. Lis le code ajouté : comment la valeur q arrive-t-elle dans la requête SQL ?
  2. Lance le serveur et teste ces recherches, depuis le dossier requetes :
curl.exe -s --get http://localhost:3004/api/recherche --data-urlencode "q=maquis"
curl.exe -s --get http://localhost:3004/api/recherche --data-urlencode "q=l'atti"
curl.exe -s --get http://localhost:3004/api/recherche --data-urlencode "q=%' OR 1=1 --"

Résultat attendu : « maquis » trouve 1 article, « l'atti » trouve 1 article sans faire planter le serveur, et l'attaque ne renvoie aucun article (et surtout pas le brouillon).

Indices

--data-urlencode encode les caractères spéciaux (espaces, %, apostrophes) pour qu'ils voyagent correctement dans l'adresse.

Si le serveur s'arrête après « l'atti », regarde le terminal : le message syntax error signe une valeur collée dans le SQL.

Correction

La bonne version utilise un ?, et place les % dans la valeur :

const q = searchParams.get("q") || "";
const resultats = db
  .prepare("SELECT id, titre FROM articles WHERE publie = 1 AND titre LIKE ? ORDER BY id")
  .all(`%${q}%`);

Si Claude a écrit LIKE '%${q}%' dans la requête, le brouillon confidentiel sort avec l'attaque. Demande alors : 

La route /api/recherche colle q dans le SQL : c'est une injection
SQL. Utilise une requête préparée avec un « ? » et passe la valeur
en paramètre. Ne change rien d'autre.

Vérifie aussi que Claude n'a pas ouvert une deuxième connexion à la base dans la route.

Exercice 3 · libre

Le blog « amélioré »

exercices/m2-03/blog-bugge/ est une version du blog modifiée par une IA, sur le port 3005. Elle a ajouté une recherche, et « corrigé » des erreurs de base de données. Trouve au moins 4 problèmes. Pour chacun, apporte une preuve : une requête curl.exe, une requête node sql.js, ou la ligne de code fautive. Puis corrige.

Résultat attendu : 4 problèmes prouvés et corrigés. L'attaque ne montre plus le brouillon, et aucune donnée orpheline n'est créée.

Pistes
  • Passe la liste « Vérifier le travail de l'IA » sur serveur.js et base.js.
  • Un commentaire « orphelin », c'est un commentaire dont l'article n'existe plus. Pour les trouver : node sql.js "SELECT c.id, c.article_id FROM commentaires c LEFT JOIN articles a ON a.id = c.article_id WHERE a.id IS NULL".
  • Un des problèmes ne se voit dans aucun test rapide : il faut lire le code.
Correction
  1. Injection SQL dans /api/recherche : LIKE '%${q}%'. L'attaque affiche le brouillon « nos tarifs 2026 (confidentiel) », et « l'atti » fait planter le serveur (near "atti": syntax error). Correction : un ? (voir exercice 2).
  2. Clés étrangères désactivées dans base.js : enableForeignKeyConstraints: false, « pour éviter les erreurs ». Conséquence : supprimer l'article 1 laisse ses commentaires orphelins, et ON DELETE CASCADE ne fonctionne plus. Correction : retirer l'option.
  3. Commentaire sur un article inexistant : POST /api/articles/999/commentaires répond 201 et crée un orphelin. La vérification « article introuvable → 404 » a disparu. Correction : la remettre, en plus de la clé étrangère.
  4. Une connexion par requête, jamais fermée : const db = ouvrir(); au début du traitement de chaque requête, sans db.close(). Et la fermeture propre au Ctrl + C a disparu. Aucun test rapide ne le montre : c'est du travail répété à chaque requête, et des connexions laissées ouvertes. Correction : ouvrir une fois au démarrage et fermer à l'arrêt, comme dans blog/.

Le point 2 est typique : face à une erreur, l'IA choisit parfois de faire taire l'alarme plutôt que de chercher la cause. Une erreur de contrainte est presque toujours une bonne nouvelle : la base vient de t'empêcher d'enregistrer des données incohérentes.

Teste-toi

1. Pourquoi les réservations de la leçon 2.1 disparaissaient-elles au redémarrage du serveur ?

Une variable JavaScript vit dans la mémoire du programme. Quand le programme s'arrête, cette mémoire est libérée. Pour garder des données, il faut les écrire dans un fichier : une base de données.

2. L'IA écrit : db.prepare(`SELECT * FROM articles WHERE titre = '${titre}'`).get(). Est-ce protégé contre l'injection ?

prepare ne voit que le texte final, où la valeur est déjà mélangée au SQL. Ce qui protège, c'est le ? : la valeur arrive séparément, et la base ne la lit jamais comme du SQL.

3. Face à l'erreur FOREIGN KEY constraint failed, l'IA ajoute enableForeignKeyConstraints: false. Bonne idée ?

La contrainte est une alarme. La couper ne règle rien : les données incohérentes (commentaires orphelins, liens cassés) s'accumulent en silence, et tu le découvres bien plus tard.
